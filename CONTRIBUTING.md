## Участие в разработке

Создавайте ветку и PR к `main`. Опишите проблему, итоговое поведение и выполненные проверки. Не включайте реальные данные ВК и секреты. Для дефекта сохранности данных добавьте регрессию с синтетическим файлом или ответом. Не удаляйте опубликованную музыку при очистке очереди, кэша или истории.

## Сборка и проверки

- Минимальная версия Android: API 34 (Android 14); target SDK: 36; compile SDK: 37.
- Gradle запускается на JDK 21; исходный и целевой Java bytecode — 17.
- Android SDK: `platforms;android-37.0`, build-tools `36.0.0`, platform-tools.
- Нужны доступ к Maven/Google и принятые лицензии Android SDK.

```sh
sdkmanager 'platforms;android-37.0' 'build-tools;36.0.0' platform-tools
python3 -m unittest discover -s tools -p 'test_*.py'
./gradlew testDebugUnitTest lintDebug lintRelease assembleDebug assembleRelease
```

Полный набор инструментальных проверок выполняется отдельно на Android 14–17 (API 34, 35, 36 и 37):

```sh
./gradlew connectedDebugAndroidTest
python3 tools/verify-instrumentation.py app/build/outputs/androidTest-results/connected
```

GitHub Actions выполняет Python/JVM-тесты, lint debug/release, release/R8, инструментальные проверки всех четырёх API и аудит зависимостей. Перед тестами `tools/interface-check.sh` сверяет фактический API запущенного эмулятора с матрицей. На каждой версии обязательны в том числе запуск пользовательской фоновой задачи с уведомлением, восстановление проверки дубликатов, фоновые операции с сохранёнными файлами и тесты MediaStore. Успех Gradle без обязательных JUnit-результатов не считается выполненной проверкой; отчёты и снимки экрана сохраняются отдельно для каждого API. Проверки подписанного обновления изменяют данные эмулятора и допускаются только на одноразовом AVD; физическое устройство для них запрещено.

Тесты используют синтетические ответы ВК и локальные аудиофайлы. Они не подтверждают реальный вход, доступность музыкальных методов, массовое скачивание, поведение конкретного телефона в фоне или результат в стороннем проигрывателе. Для этого нужна отдельная ручная приёмка точного APK.

## Сохранность файлов и очереди

Очередь и учёт файлов хранятся в приватной SQLite-базе в `noBackupFilesDir`: транзакции, WAL и `synchronous=FULL`. Ключ задачи учитывает аккаунт, тип и ID источника, ID трека и номер его вхождения. Порядок и название не определяют идентичность. Источники с одинаковым видимым названием получают устойчивые отдельные каталоги; старые файлы не переименовываются автоматически.

Запись MediaStore сначала скрыта через `IS_PENDING`. После записи проверяются размер и SHA-256, сохраняется контрольная точка, затем файл публикуется. Android может уточнить имя при публикации: окончательные `DISPLAY_NAME` и `RELATIVE_PATH` перечитываются и сохраняются. Восстановление принимает изменённые метаданные только после проверки владельца, допустимой папки, размера и хеша. Нельзя восстанавливать уже удалённую из учёта запись или принимать чужой файл по похожему имени.

Повторное использование файла требует проверки целостности. Старый внутренний архив переносится в общую музыку с сохранением оригиналов; повреждённый индекс и неперенесённые записи допускают ручное сохранение копии. Автоматический поиск перемещённого файла принимает только единственное подходящее совпадение; ручной выбор создаёт подтверждённую собственную копию.

Один URI может иметь несколько строк `files`: строка представляет вхождение в источник, а не отдельный физический файл. `SavedAudioReuse` связывает одинаковый ID ВК и проверенную длительность с уже проверенным URI; порядок и повторные позиции описывает M3U8. Первоначальная папка сохраняется. Разные ID и совпадение только имени не дают автоматического объединения. Изменение обложки, перемещение или подтверждённое восстановление обновляют все ссылки со старым URI и одинаковыми контрольными данными одной транзакцией, включая prepared, историю и счётчик обложек. Очистка истории не отменяется повторным использованием. Забывание одной ссылки не удаляет общий файл и другие ссылки.

Изменение пути сохраняет `m3u-relocation` в той же транзакции. `SharedPlaylistStore.repairLocations` применяет переносы в порядке записи ко всем прежним плейлистам из учёта, включая предыдущие очереди. Меняются только точные строки относительного пути и связанная длительность EXTINF; порядок и повторы сохраняются. Читаются только собственные опубликованные файлы с проверенными размером/SHA-256 до 4 МиБ. Публикация использует прежний pending/checkpoint-протокол. Изменённый пользователем M3U8 сохраняется, соответствующий перенос остаётся в журнале и возвращает проблему; другие неизменённые плейлисты обрабатываются конечным проходом.

`PublishedAudio.catalogueVerified` отделяет сохранённый оригинал от принятой пользователем локальной замены. Неточное ручное восстановление устанавливает false у всех ссылок, точное сохраняет прежнее значение. Копирование, связывание, обложки и перенос не повышают доверие. `LibraryRemovalProtocol` отказывает для false, даже если источник ссылки — «Моя музыка». Старые записи в папке «Восстановленные» без нового поля читаются как неподтверждённые. JSON-отчёт добавляет одноимённое поле; формат/длительность проверяются независимо от происхождения.

Дальнейшее объединение внешней медиатеки требует отдельного интерфейса выбора папки через Storage Access Framework и долговременного разрешения на чтение. Сначала строится локальный индекс с размером, фактической длительностью, тегами и хешем аудиоданных без ID3; это отличается от SHA-256 всего файла для контроля целостности. Разные кодировки и ремиксы требуют отдельного сравнения и решения пользователя. Перед очисткой готовых дублей нужен предварительный список сохраняемых/удаляемых файлов, количества ссылок и освобождаемого места; внешние файлы не удаляются без системного подтверждения. Импорт, анализ внешней папки и очистка старых копий пока не реализованы.

Недоступность источника и несовпадение длительности — разные состояния. `INCOMPLETE` не доказывает отсутствие записи в ВК: это может быть preview, обрыв, проблема контейнера или метаданных. `ExportFailureDetails` сохраняет только числовые измерения длительности, фиксированную причину `TrackUnavailable` или HTTP-статус медиасервера в SQLite meta для текущей очереди; новый выбор очищает старые подробности, успешный повтор удаляет подробности задачи. Они отображаются в очереди и добавляются как `errorDetails` в JSON-отчёт без изменения прежних полей и schema=1. Подмена альтернативной версией требует выбора пользователя и отдельной идентичности источника; её нельзя отмечать как проверенный оригинал ВК. Общая локальная копия может использоваться без повторного сетевого доступа, даже если запись позднее стала недоступна на сервере.

Для будущей интеграции SoundCloud необходимо сначала согласовать допустимый сценарий: [API Terms, Caching and Downloading](https://developers.soundcloud.com/docs/api/terms-of-use) запрещают офлайн-сохранение аудио через API даже при разрешённых загрузках на сайте. Наличие download endpoint в OpenAPI не снимает этого ограничения. Поиск с открытием оригинальной страницы и импорт файла, самостоятельно сохранённого пользователем, являются отдельными сценариями; они пока не реализованы. Официальный OAuth требует зарегистрированного приложения и конфиденциального client secret; секрет не должен попадать в APK, исходники или журналы. Аккаунт SoundCloud этим изменением не подключается.

Состояние постановки UIDT-задачи сохраняется и при отмене coroutine. Доступ и владелец очереди проверяются при работе. Другой аккаунт не наследует очередь или согласия. Ошибки HTTP медиасервера относятся к конкретному файлу: ссылка ограниченно обновляется, затем задача помечается ошибкой и очередь идёт дальше. HTTP 401/403/404/410 медиасервера означают недоступность файла, а не отказ токена ВК; ограничение частоты, потеря сети и настоящий отказ доступа по-прежнему приостанавливают очередь. При отказе хранилища/доступа очередь приостанавливается; текущий незавершённый трек скачивается заново без HTTP Range или продолжения HLS по сегментам.

Страницы каталога проверяются на преждевременный конец и повтор одной страницы. Полнота считается по полученным позициям, а отображение — по уникальным ключам: перекрытие страниц не даёт ложного недобора. `MusicCatalog.load` сверяет все подборки с серверным `audio.getPlaylists(filters=albums)`, включая ключи оригиналов сохранённых источников; числовые типы не угадываются по названиям или старому ручному выбору. При отсутствии подтверждённого типа доступен общий раздел «Подборки». Каталог не является атомарным снимком ВК.

`CatalogDownloads` скрывает источник только при совпадении аккаунта, текущих ID/вхождений и длительностей всех треков, проверенных аудиофайлах и точном актуальном M3U8. Одинаковое название, количество или статус старой очереди не доказывают полноту. История файлов не создаёт позиции каталога. Обновление сбрасывает старое выделение и каталог перед запросом; ошибка не оставляет старые данные актуальными. Массовая подготовка повторяет проверку и пропускает только подтверждённые полные источники. Пустой результат не заменяет старую очередь. Полнота аудио сопоставляется с длительностью каталога, для HLS — также с манифестом. Короткий preview не принимается за полную песню. M3U8 содержит относительные пути, исходный порядок и повторы; неполная выгрузка обозначается явно. Изменённый пользователем плейлист не удаляется автоматически.

## Вход и сетевые границы

Вход использует Chrome Custom Tab, опрос состояния заявки и нативный обмен результата. Открытие браузера или HTTP 200 не доказывает вход: доступ сохраняется только после проверки `users.get`/`audio.get` и аккаунта. Пароли и коды не собираются через собственную веб-форму. Чтение cookies/DOM профиля Chrome не используется.

Токены и ограниченный материал нативного обмена зашифрованы AES-GCM через Android Keystore в `noBackupFilesDir`. Новый ручной доступ проверяется до замены старого. Повреждённый конверт обрабатывается отдельно и не мешает новому входу. Удаление локального доступа не отзывает серверные сеансы.

При известном сроке продление пробуется за пять минут до истечения и после отказа доступа. Нет отдельного постоянного фонового таймера; срок проверяется при активном интерфейсе и перед музыкальными запросами. Новый результат должен принадлежать прежнему аккаунту. Сохранение сравнивает прежний конверт, поэтому поздний ответ не отменяет выход или новый вход. Одновременные попытки объединены mutex; повтор запроса ограничен. Сетевой сбой сохраняет ещё действующий доступ, а отказ обмена требует нового входа.

Музыкальный протокол внутренний и не имеет гарантии стабильности публичного API. Запросы направляются только на фиксированные HTTPS-адреса; ответы, перенаправления, размер, глубина JSON и частота запросов ограничены. Секреты API не передаются CDN обложек, аудио или обновлятору. Полная ссылка на песню разбирается локально в точный ID: исходный произвольный URL не открывается клиентом. Права поиска и чтения определяет ВК.

## Обложки и сравнение аудио

`TrackMetadataBatch` сохраняет в SQLite отдельный курсор для аккаунта: снимок целей, следующую позицию и результаты, без токенов или подписанных адресов. Системная/сетевая ошибка и отмена оставляют текущую цель необработанной. Возобновление после явного входа заново требует подтверждённого `users.get`/`audio.get` владельца и повторной проверки локального файла. Готовые цели пропускаются; сбой между записью файла и фиксацией курсора может потребовать одной повторной проверки текущего файла, но не его повторного скачивания или потери звука.

Перед запросами и записью названий применяется `MusicSessionManager.continueRead`. Зашифрованный `read_session_id` сохраняется только после проверенного продления; новый вход создаёт другую сессию, даже для того же владельца. Старые конверты читаются с ID прежнего доступа в качестве исходной сессии. Граница чтения не зависит от количества ротаций токена. Упреждающее продление использует 1/5 известного времени жизни (не более пяти минут), а пауза после временной ошибки ограничена оставшимся сроком токена.

`NativeTrack` хранит исходные `title` и необязательный `subtitle` отдельно, `displayTitle` объединяет их без повторного добавления уже имеющейся пометки. Очереди и индексы без нового поля читаются с `null`; ID задач от текста не зависит. Имя, теги MP3/M4A, интерфейс и M3U8 используют полное название. Разрешение медиа сохраняет известную пометку, если свежий ответ вовсе не содержит `subtitle`.

Перед перезаписью тегов `TrackMetadataRepair` устанавливает `IS_PENDING=1` у проверенного собственного URI. Запись и переименование выполняются до снятия флага; публикация сканирует уже окончательный путь. Так асинхронный сканер после закрытия дескриптора не пытается прочитать старое имя. Журнал восстанавливается до очистки незавершённых публикаций: проверенный результат публикуется, частичная запись заменяется резервной копией. Файлы с активным журналом не считаются брошенными загрузками.

`TrackMetadataRepair` обновляет названия существующих файлов по точному ID и совпадающей длительности. Он не запрашивает медиапоток и не ищет похожие записи. Перед записью проверяет исходный хеш, сохраняет резервную копию и AtomicFile-журнал вне кэша; при восстановлении завершает подтверждённую запись либо возвращает исходные байты. MP3 сохраняет APIC и неизвестные кадры ID3v2.3/v2.4, M4A — обложки и остальные метаданные, а контрольная подпись аудио остаётся прежней. Изменение имени перечитывает фактический результат MediaStore, сохраняет URI и не перезаписывает конфликтующий файл. Индекс, задачи и все ссылки на один URI обновляются транзакцией, прежние M3U8 — через устойчивые маркеры, включая изменение EXTINF без переименования. Редактирование сериализовано с загрузками, восстановлением и обложками через `AudioExportRuntime.editSaved`.

Размер аудиозаписи не ограничен фиксированной квотой: сеть, обработка и публикация используют потоковые буферы, размеры/смещения — Long. `AudioStorage` проверяет запас места с защитой арифметики от переполнения. Общего дедлайна медиафайла нет; connect/read timeout, отмена задачи, пределы метаданных и проверка полноты обязательны. Перед повтором очереди DONE проверяется по реальным байтам. Перемещения восстанавливаются только по размеру и SHA-256 среди собственных доступных MediaStore-записей. Файлы с чужим владельцем не принимаются по имени и не перезаписываются; для них остаётся явный выбор через системный диалог.

MP3 получает APIC, M4A — `covr` и текстовые теги; аудио не перекодируется. При смещении `mdat` корректируются таблицы смещений. Структура файла и неизменность аудиобайтов проверяются перед публикацией. Изображения ограничены по размеру/пикселям, принимаются только с разрешённых HTTPS-серверов; перенаправления проверяются повторно.

Для изменения существующего файла обязательны проверка владельца/пути/размера/SHA-256, резервная копия и журнал восстановления. Перед записью повторно проверяются активность приложения, поколение операции и текущий доступ. Ручной выбор источника картинки одноразовый: результаты действуют 10 минут, просмотренная картинка — 5 минут; смена запроса, доступа или уход в фон сбрасывают выбор. Он не заменяет ID аудио и не изменяет библиотеку ВК.

Дубликаты отбираются по нормализованным названию и исполнителю, затем сравниваются по формату и контрольной подписи аудио. Для M4A учитываются конфигурация декодера, размеры/расположение сэмплов и временная шкала. Это точное сравнение, не акустический отпечаток. Частичные результаты не принимаются.

UIDT-поиск хранит до 20 000 контрольных результатов на 24 часа для аккаунта и точных метаданных каждой записи; перестановки и изменения других записей не сбрасывают готовые проверки. Удалённая или изменённая запись теряет только собственную квитанцию; полные аудиокопии после проверки удаляются. Согласия на удаление не сохраняются. Перед каждым удалением обе записи загружаются заново и проверяются с одноразовым подтверждением в активном приложении. Автоматического повтора серверного удаления нет. Поиск имеет конечный проход: итоговая проверка списка исключает изменившиеся/исчезнувшие записи из предложений удаления и не перезапускает хеширование. Общая блокировка исключает одновременную загрузку и конфликтующие операции с файлами.

## Диагностика и приватность

В событиях допускаются фиксированные этапы/коды, счётчики и HTTP-статусы. Нельзя записывать токены, cookies, подписанные URL, тела ответов, пользовательские запросы или произвольный текст исключений. Журналы ограничены по размеру и сохраняются асинхронно: отсутствие завершающего события не доказывает crash.

Текущий и предыдущий запуски экспортируются раздельно с разными run ID. FileProvider даёт временное чтение только выбранного отчёта. Отчёт результата выгрузки намеренно содержит названия, account ID и относительные пути; интерфейс предупреждает об этом. Правила хранения и удаления описаны в [PRIVACY.md](PRIVACY.md), приватное сообщение об уязвимости — в [SECURITY.md](SECURITY.md).

## Зависимости и источники

Зависимости закреплены версиями, lock-файлом и SHA-256; Actions — полными SHA. Обновления сопровождаются проверкой источников, изменением lock/checksum и SBOM/SCA. Обычный CI не генерирует доверенные checksum автоматически. Исправления уязвимостей classpath инструмента lint заданы отдельно в `app/build.gradle.kts` и не означают добавления этих библиотек в APK.

Лицензии и обязательные уведомления зависимостей сохраняются в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md), [NOTICE](NOTICE) и ресурсах APK. Полезные первичные источники для сопровождения:

- [Общие медиафайлы Android](https://developer.android.com/training/data-storage/shared/media), [UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt), [Chrome Custom Tabs](https://developer.chrome.com/docs/android/custom-tabs).
- [Схемы API ВК](https://github.com/VKCOM/vk-api-schema); наличие схемы объекта не гарантирует доступность музыкального метода.
- [AIMP VK: контракт поиска аудио](https://github.com/ArtemIzmaylov/aimp_VK/blob/main/AIMP.VK.Core.pas).
- [Нативный обмен музыкального доступа](https://github.com/vodka2/vk-audio-token); это технический источник исследования, не обещание совместимости сервера.
- Источники исправлений classpath lint: [Apache Commons](https://svn.apache.org/repos/infra/websites/production/commons/content/proper/commons-lang/security.html), [Apache HttpClient](https://www.openwall.com/lists/oss-security/2020/10/08/4/), [Bouncy Castle](https://www.bouncycastle.org/resources/new-release-bouncy-castle-java-1-85/).

## Выпуск релиза

Push в `main` и pull request выполняют проверки и не публикуют стабильный APK. В workflow **Android checks and APK** ручной запуск с `channel=checks` тоже только проверяет код. `channel=rc` на `main` создаёт подписанный prerelease с суффиксом `-rc`, не меняет Latest и встроенный канал обновлений.

Для сборки нужны JDK 21, Android SDK `platforms;android-37.0`, build-tools 36.0.0, постоянный ключ из `ANDROID_SIGNING`. Исходный/целевой Java bytecode остаётся 17. `versionName` меняется в `version.properties`, CI выдаёт монотонный `versionCode=1000+run_number`; номера не переиспользуются. Локальный номер — только запасное значение для разработки.

### Проверки перед RC

1. Python-тесты инструментов, JVM debug, lint debug/release, сборка release с R8.
2. Все инструментальные тесты на API 34, 35, 36 и 37, включая обязательные регрессии аудита, восстановления доступа, фоновых задач с уведомлениями и окончательных имён MediaStore; полный перечень задаёт `tools/verify-instrumentation.py`. Пропуск или отсутствие отчёта считается ошибкой.
3. Строгая проверка SHA-256 зависимостей и зафиксированных версий, SBOM CycloneDX, полный OSV scan. Ошибка сети сканера не равна отсутствию уязвимостей.
4. Подписанное обновление `adb install -r` на одноразовом AVD с текущего stable и самой старой поддерживаемой контрольной версии 0.9.5/1087: данные/очередь, безопасная миграция архива, журнал после force-stop. Используется настоящий APK из Releases и закреплённый сертификат. Версия 0.9.5 может храниться как закрытый Draft: CI получает её по фиксированным release/asset ID с существующим токеном задачи, проверяет SHA-256, затем подпись. Публичное скачивание старого APK для этой проверки не требуется.

Проверка подписанного обновления остаётся на API 36: предыдущие контрольные APK требуют Android 16 и не устанавливаются на API 34/35. Новая установка и полный набор инструментальных тестов проверяются на всех четырёх API. `build-info.json` получает `minSdk` из фактического APK, а не из константы; значение сверяется с `app/build.gradle.kts`. Минимальный SDK предыдущего стабильного APK может отличаться от нового.

При обновлении зависимостей запустить на доверенной машине `./gradlew --write-verification-metadata sha256 --write-locks testDebugUnitTest lintDebug lintRelease assembleDebug assembleRelease assembleDebugAndroidTest writeDependencyInventory`. Проверить источники и изменения checksum/lock, закоммитить оба файла. Не принимать автоматически новый checksum при ошибке верификации. Actions закреплены полными SHA; Dependabot предлагает обновления в PR.

### Ручная приёмка точного APK

Установить опубликованный RC на реальном устройстве. Не очищать данные основной установки ради теста; использовать резервную копию и тестовый аккаунт там, где возможно. Заполнить `docs/release-acceptance/current.json` только фактическими результатами: исходный SHA из build-info, versionCode, SHA-256 именно установленного APK, номер Actions run, дата, проверяющий, модель и версия Android. Не включать токены, подписанные URL и приватные названия композиций.

| Сценарий | Что зафиксировать в evidence |
|---|---|
| Вход и продление ВК | Новый вход, успешная проверка account ID, истёкший/отклонённый доступ, повторный выпуск или понятный запрос нового входа; отказ нового ручного токена сохраняет старый |
| Массовая библиотека | Библиотека не менее 4449 позиций либо документированное обоснование меньшего реального объёма; числа задач/готовых/ошибок/источников, сверка результата |
| Фон и перезапуск | Не менее часа с выключенным экраном, системная остановка/force-stop и ручное продолжение; производитель устройства и настройки батареи |
| Потеря сети | Wi-Fi → offline → mobile/Wi-Fi, повтор без потери DONE и лишних копий |
| Смена аккаунта | Очередь A не выполняется с B; старой неподписанной очереди требуется явная привязка; удаление доступа не удаляет музыку |
| Обновление архива | `install -r`, сохранность оригиналов и индекса, повтор после нехватки места/порчи индекса, ручное сохранение оставшегося файла |
| Внешние проигрыватели | Названия двух проигрывателей и версии; Unicode title/artist/album/cover MP3/M4A, относительный M3U8 и повторяющиеся позиции |
| Дубликаты и удаление | Разная конфигурация M4A не совпадает; подтверждение удаления только выбранной записи ВК; локальные файлы остаются |

Если сценарий не выполнен или провален, оставить `pending`/`failed`. CI не выдаёт эти результаты за ручную приёмку.

### Продвижение в stable

После ревью коммита с evidence запустить **Verify RC or promote accepted APK to stable**, `channel=stable`, `candidate_run` — run с принятым APK. Текущий stable и старая контрольная версия скачиваются заново через GitHub Releases API; закрытая контрольная версия доступна токену CI: устаревший номер Actions run не может подменить актуальную базу обновления. Workflow повторно проверяет происхождение, подпись и обновление, а затем публикует **тот же APK**, не пересобирает его. Android/build inputs между исходным SHA APK и коммитом проверки должны совпадать. Любое изменение приложения, ключа, Gradle/checksum/lock требует нового RC и приёмки. Pending evidence блокирует stable.

При продвижении зависимости принятого APK повторно сканируются по его SBOM.

В Releases прикладываются только APK и `SHA256SUMS.txt`. В описании остаются ссылки на исходники точного коммита APK, инструкцию сборки и запуск CI. Лицензия и уведомления правообладателя входят в APK и архив исходников. Полный набор доказательств (build-info, upgrade-check, публичный сертификат, SBOM, OSV, LICENSE и NOTICE) обязателен перед публикацией и сохраняется в артефактах CI `VK-Music-Export-release` или `Verified-release`; срок хранения — 30 дней. Примечания берутся только из точного раздела версии в `CHANGELOG.md`; отсутствие раздела блокирует выпуск. Предыдущий Latest не откатывается старым повтором workflow. Закрытый ключ в артефакты не попадает.

### Защита main

Подготовлен `.github/main-ruleset.json`: PR с ревью, обязательные `build`/`interface`, запрет удаления/force-push, разрешение обсуждений. Администратор применяет его через Settings → Rules → Rulesets или `gh api --method POST repos/alcovaibe/vk-music-export/rulesets --input .github/main-ruleset.json`. Для правила обязательного одобрения нужен второй ревьюер. Сам файл в PR не включает защиту на GitHub; состояние проверяется отдельно администратором. Бот обновления канала использует отдельный PR, поэтому защита не требует обхода main.

Для PR канала в Settings → Actions должен быть разрешён пункт «Allow GitHub Actions to create and approve pull requests». Проверки его ветки запускаются явным workflow_dispatch; они не обходят требуемое ревью. Если настройка запрещена, stable APK остаётся в Releases, а обновление канала нужно завершить через обычный PR.

### Архив старых релизов

Workflow `Archive releases before 0.10.0` переводит версии строго младше 0.10.0 в Draft; 0.10.0 и новее, теги, исходные вложения и Latest сохраняются. Режим `plan` выполняет только проверку, `hide` применяет изменения. Старые APK из артефактов Actions сначала сохраняются побайтово как ZIP-вложения закрытого черновика с проверкой SHA-256; только затем снимается публичный доступ к исходному артефакту. Отчёт `Release-archive-audit` содержит метаданные, без APK и архивов с бинарниками.

Исходники по тегам публичного репозитория остаются общедоступными. Повторная публикация черновика возвращает доступ к его файлам.

## Сопровождение документации

[README.md](README.md) — единое актуальное руководство по возможностям, использованию и ограничениям. Здесь сохраняются текущие технические контракты и порядок сопровождения. Не добавляйте отдельные файлы по версиям, отчёты переписки и сравнения с другими приложениями автора. Исторические расследования можно найти в Git.

`CHANGELOG.md` остаётся журналом выпусков и источником release notes для автоматизации: для выпуска нужен точный раздел `versionName`. Это не пользовательское руководство. При изменении поведения обновляйте соответствующий раздел README и запись предстоящего выпуска; не подменяйте текущую инструкцию историей исправлений.

В `docs` остаются только машинные данные: `updates/android.json` — публичный канал обновлений, `release-acceptance/current.json` — фактические результаты ручной приёмки. Их пути используются приложением и инструментами; переносить их вместе с Markdown нельзя. Не включайте в публичную приёмку личные данные проверяющего сверх необходимого: используйте псевдоним.

### Сборка из ветки PR

Владелец может вручную запустить `Android checks and APK` с `channel=rc`, выбрав ветку этого же репозитория. Обычные PR и push без явного запроса не получают ключ подписи и не публикуют релиз. RC проходит те же JVM/lint/R8, API 34–37, проверку постоянного сертификата и реальное обновление с текущего stable и старой поддерживаемой версии. Выбор ветки не отменяет проверок точного APK или требований ручной приёмки для автоматического stable.

### Подписки исполнителей

`MusicArtists` разбирает `catalog.getAudio`, адресные секции и курсоры блоков. Корневой пул `artists` сам по себе не является списком подписок: учитываются ссылки из раздела музыкальных подписок; явный `is_following=false` исключает отписанных исполнителей. Неизвестный формат/недоступный метод показывается как ошибка, а не пустая успешная библиотека. Нет подписки/отписки, рекомендаций или переходов по имени в строке песни. Контракт проверен синтетическими ответами; доступность для реального аккаунта зависит от ВК.

Однократная публикация PR #48 разрешена владельцем как Latest без слияния. Из-за недоступности браузера запуск выполняется push-коммитом `[publish-pr-48]` только в `codex/music-library-redesign`. Перед ключом проверяются ограниченный по времени запрос `docs/release-requests/pr-48.json` и точные Git-объекты всех входов Android-сборки. После обычного RC проходят подпись, обе версии Android и обновление с двух базовых APK; затем тот же APK публикуется как Latest с явной пометкой о неподтверждённой ручной приёмке. Общий `release_gate.py` не изменён. Обычные PR и push без маркера не запускают подпись.
