# Встроенные обложки — 0.9.11

## Новые загрузки

Обложка берётся только из thumb точного трека либо album.thumb в ответе audio.getById. Проверяются ID и длительность; картинки подборки, поиск по названию и подстановка обложки плейлиста отсутствуют. Наибольший доступный размер выбирается из photo_1200/600/300/270/135/68/34. При первичном разрешении аудиоссылки данные картинки остаются в небольшом кэше памяти; подписанные ссылки не сохраняются в SQLite и диагностике. Скачанная картинка ограничена 2 МиБ и 4096×4096 (не более 16 млн пикселей), нормализуется в JPEG до 1024 по большей стороне. Только HTTPS и разрешённые домены изображений ВК; каждый redirect проверяется повторно. API-токен, cookies и пользовательский User-Agent к CDN не пересылаются.

MP3 получает APIC в ID3v2.3/v2.4. Существующие текстовые теги и байты после ID3 сохраняются. M4A получает moov/udta/meta/ilst/covr; прочие теги сохраняются, stco/co64 корректируются при смещении mdat. Аудиокодек не запускается. SHA-256 звуковой части (MP3 payload / MP4 mdat) обязан совпасть; встроенная картинка проверяется до публикации. Неизвестные/небезопасные структуры не переписываются. Для новых сохранений ошибка картинки оставляет проверенный аудиофайл без добавленной обложки. Существующий путь MediaStore IS_PENDING и контрольная точка публикации сохранены.

В итогах очереди показаны файлы с добавленной обложкой и без неё. Последние сохранённые файлы имеют такую же подпись. Это сведения внутреннего учёта, а не обещание того, что каждый сторонний проигрыватель немедленно обновит свой кэш.

## Уже сохранённые файлы

Кнопка «Добавить обложки к сохранённым» в музыкальном разделе открывает отдельную нижнюю панель. Только явное нажатие «Добавить обложки» начинает обработку всех файлов из files в audio-export.db. История последних пяти не ограничивает этот список; её очистка не мешает обработке. Неизвестные приложению файлы и файлы после потери/сброса учёта не сопоставляются по имени. С 0.9.13 для сохранённого учёта есть [отдельная проверка и восстановление связи](FILE-RECOVERY.md). Новых разрешений на общую медиатеку нет.

Каждый файл должен принадлежать пакету приложения и лежать под Music/VK Music Export; с 0.9.13 отдельно восстановленная точная связь может указывать на собственный файл в другой папке Music. Перед чтением/записью проверяется исходный размер/SHA-256. Изменённый пользователем или отсутствующий файл пропускается с ошибкой. Имеющаяся встроенная обложка не заменяется. Недоступный в ВК трек либо отсутствие thumb дают пропуск без изменения музыки; это относится и к трекам, которые ранее удалили из ВК. Повторной загрузки аудио нет.

Исходник копируется в noBackupFilesDir/artwork-repair/original.audio, сверяется хеш и создаётся отдельный полностью проверенный tagged.audio. Требуется место примерно на две дополнительные копии текущего файла плюс запас 8 МиБ. AtomicFile transaction.json сохраняет старый/новый размер и хеш до первой записи. Затем обновляется содержимое прежнего MediaStore URI, выполняются fsync и повторная проверка. В SQLite транзакционно заменяются целостность/метка обложки, связанные checkpoints и только существующие элементы истории. Имя, папка, URI и задача сохраняются. Изменение тегов не возвращает очищенную историю и не удаляет локальную музыку.

Это восстановимая запись в прежний URI, а не атомарный rename MediaStore. Если процесс погиб во время записи, до следующего запуска файл может быть неполным. Восстановление выполняется перед очередью: полностью записанный новый файл принимается с новым хешем; иначе проверенная резервная копия возвращается. При невозможности восстановления резервная копия и журнал сохраняются, очередь блокируется ошибкой STORAGE. Освободи место и перезапусти приложение; не очищай его данные, пока требуется резервная копия. Абсолютную сохранность при неисправности накопителя/сбросе данных платформа не гарантирует.

Обработка старых файлов и запуск UIDT взаимно исключаются общим управлением очередью. Готовая/приостановленная очередь сохраняется, активную сначала нужно приостановить. Нижняя панель показывает прогресс и добавленные/существующие/отсутствующие/ошибочные обложки. «Свернуть» закрывает только панель. Уход с музыкального экрана/в фон или «Остановить» прерывают обработку с восстановлением текущей записи. Следующий явный запуск пропускает уже готовые файлы.

## Подтверждения и источники

Проверки используют синтетические ответы ВК/CDN и реальные тестовые MP3/M4A/JPEG в MediaStore. Проверяются встроенная картинка и длительность через MediaMetadataRetriever, неизменность аудиобайтов/имени/URI, обновлённый SHA-256, сохранение очищенной истории, отказ при небезопасном redirect/картинке и восстановление после частичной/полной прерванной записи. Это не проверка реального аккаунта, реальных прав ВК или проигрывателя владельца.

- ID3 APIC: https://id3.org/id3v2.3.0#sec4.15
- M4A covr: https://mutagen.readthedocs.io/en/latest/api/mp4.html
- Наблюдаемая структура Audio.thumb/Album.thumb и photo_* в первичном исходнике клиента: https://github.com/ilyhalight/vk-audio/tree/113cb12e7470809eb0f9a09c96b7d0870c2575b5/src/types/api/audio
- Запись MediaStore: https://developer.android.com/reference/android/provider/MediaStore#openFileDescriptor(android.content.ContentResolver,android.net.Uri,java.lang.String,android.os.CancellationSignal)

## Диагностика с 0.9.12

«Ошибки: N» — число файлов, обработка которых завершилась ошибкой, а не код ответа ВК. В 0.9.11 причины этих пропусков не записывались; HTTP 200 и число байтов ответа не позволяют восстановить их задним числом. Эти журналы не доказывают ни сохранность каждого файла, ни успешность добавления картинок.

Новая панель показывает последние десять проблемных файлов с причиной, кодом и этапом. Имена остаются только в UI. В журнале audio_artwork_item — случайный ID операции, порядковый номер, фиксированный этап/результат, MusicError/kind и числовой код ВК, если он известен. audio_artwork_summary содержит результат COMPLETED/STOPPED/INTERRUPTED и счётчики, включая прерывание через finally. URL, имена, тело ответа, сообщения исключений и секреты не записываются. Полный смысл каждого непредвиденного ответа ВК по этим кодам не гарантируется, но теперь различимы проверка файла, резервная копия, чтение тегов, разрешение/получение/декодирование картинки и этапы записи.

Пустой audio.getById (response=[]) означает, что ВК не вернул трек; он учитывается как недоступный, а не как неизвестная ошибка формата. Ответ другого типа, несколько треков или несовпадение идентичности остаются ошибками. Уход с музыкального экрана или сворачивание по-прежнему прерывают обработку старых файлов; это отдельное событие, не причина автоматически объявлять все файлы ошибочными. Результат панели сохраняется в текущем ViewModel до нового явного запуска, а не в отдельном постоянном списке.

С 0.9.13 общий INCOMPLETE на этапе VERIFY_FILE дополнен точным file_reason: отсутствие, отказ доступа, владелец/папка/публикация, размер, хеш или ошибка чтения. Для перемещённых файлов предусмотрено отдельное восстановление связи, без отключения проверок перед записью обложки.

## Результаты с 0.9.14

Панель сохраняет в текущем ViewModel полные отдельные списки всех пропусков и ошибок. Название и исполнитель берутся из сохранённой записи трека, а не угадываются из имени файла. Список ленивый, заголовок панели остаётся над прокруткой. Результат можно вновь открыть до нового запуска обработки/потери ViewModel; сохранение результатов между запусками приложения не добавлено.

- «ВК не передал обложку»: точный трек вернулся, но API не передал поддерживаемую ссылку thumb трека/альбома. Это не утверждение об отсутствии картинки в интерфейсе ВК.
- «Треки недоступны»: ВК не вернул трек для текущего доступа (в том числе response=[]). Это не доказательство удаления аудиозаписи со всего ВК.
- Ошибка получения картинки: API дал адрес, но сервер/перенаправление/декодирование не позволили получить изображение. HTTP-ошибка не переводится в «обложки нет».

HTTP-ошибки содержат числовой http_status и фиксированный fetch_reason: HTTP_STATUS, REDIRECT_LIMIT, REDIRECT_LOCATION_MISSING, REDIRECT_UNSAFE. Значения показаны понятным текстом в панели и передаются обезличенно в audio_artwork_item. При HTTP 404/410 явно указано отсутствие картинки по переданному адресу, при HTTP 401/403 — отказ сервера картинки; истечение музыкального токена из этого не выводится. Подсказка из первичного audio.getById потребляется один раз и сохраняет результат разбора, включая ошибку. Следующая отдельная попытка запрашивает свежие метаданные; ошибка разбора не превращается в отсутствие картинки через кэш. Небезопасные адреса/redirect по-прежнему отклоняются; предложенный небезопасный thumb теперь MEDIA_URL, а не ложный пропуск без картинки. URL, имена, исполнители, названия, cookies, токены и тела ответов в новые события не попадают.

Для отсутствия ссылки результат audio_artwork_item теперь NO_COVER, для недоступного трека — UNAVAILABLE. В summary добавлены no_cover и unavailable; missing остаётся их суммой для совместимости. Все прежние проверки файлов, резервная копия/журнал восстановления и лимиты изображения сохраняются.

Два HTTP-отказа владельца в 0.9.13 не позволяют восстановить реальные коды задним числом. Наличие/отсутствие обложки в интерфейсе ВК не заменяет повторную проверку нативного API/CDN на устройстве.
