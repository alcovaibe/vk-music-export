# Вход через Chrome — эксперимент 0.8.1

## Исправление по реальному логу 0.8.0 (1054)

Подтверждённая последовательность на SM-S731B / Android 17: native_auth_start в 17:47:37.047556Z → PREPARING → bootstrap HTTP 200, 6411 байт в 17:47:38.507944Z → RESPONSE через 2,574 мс. До READY, открытия Chrome, создания заявки и проверки музыки выполнение не дошло. Потерь событий и ошибок журнала нет. Начальный network_blocked=true сменился false до нажатия входа; этот лог не доказывает проблему VPN или Chrome.

Публичная проверка 20 октября 2026 года воспроизвела HTML /qr_auth размером 6411 байт без anonymous_token и code_auth_verification_hash. Добавление initial_stats_info и сравнение заголовков мобильного/настольного Chrome результат не изменили. В свежем Chrome без аккаунта страница загрузила модуль VK ID и выполнила другой bootstrap:

1. auth.getAnonymToken, версия 5.276 → response.token.
2. auth.getQrAuthData, версия 5.276 → response.code_auth_verification_hash.
3. auth.getAuthCode, версия 5.126 → одноразовая заявка.
4. auth.checkAuthCode с web_auth=1, версия 5.126 → status=0, ожидание подтверждения.

Те же cookie-free JSON-запросы с собственным User-Agent приложения проверены отдельно от браузера: HTTP 200 на всех четырёх этапах. В актуальном ответе expires_in является временем Unix в секундах (остаток 180 секунд), а auth_url использует точный узел qr.vk.ru. Старый код отклонил бы срок и этот узел даже после исправления HTML-парсера.

0.8.1 использует фиксированные JSON-методы вместо чтения HTML. Точная HTTPS-проверка разрешает qr.vk.ru; поддомены похожих посторонних сайтов, userinfo, HTTP и нестандартные порты отклоняются. Абсолютное время один раз переводится в остаток по системным часам и далее в монотонный deadline, максимум 5 минут. Исторический относительный срок также поддержан; истёкшие, слишком далёкие и переполняющие значения отклоняются.

Исследовательская ветка содержит [проверки публичного протокола](https://github.com/alcovaibe/vk-music-export/tree/investigate-vk-bootstrap-20261020). Они не используют профиль владельца, не подтверждают заявку и сохраняют только метаданные. Это доказательство исправления подготовки заявки, не успешного входа и не доступности audio.get. Предположение о блокировке HTML-парсинга настройками безопасности аккаунта этим исследованием не подтвердилось: отсутствие старых полей воспроизводится без аккаунта.


Проверка действительного Kotlin-клиента, а не только эквивалентного скрипта: [Actions 39474209625](https://github.com/alcovaibe/vk-music-export/actions/runs/39474209625), 10 регрессионных тестов и 1 публичный сетевой тест, без ошибок и пропусков. Последовательность anonymous / qr_bootstrap / create / poll дала HTTP 200, монотонный остаток около 179 секунд и status=0. Учётная запись, подтверждение и музыкальный API не проверялись.

## Пользовательский сценарий

Настройки теперь отдельный экран. Подстраницы музыкального доступа, обновлений и ручного ввода токенов также занимают весь экран; «Назад» возвращает к предыдущей странице. Экран настроек восстанавливается после пересоздания Activity. Значения секретных полей в saved state не попадают, а страницы ввода защищены FLAG_SECURE.

Настройки → «Прямой доступ ВК · эксперимент» → «Подключить ВК через Chrome» → «Открыть подтверждение ВК». В Chrome нужно проверить адрес ВК, подтвердить свою заявку и вернуться в приложение. Ввод пароля и кодов остаётся на стороне ВК. Если Chrome уже авторизован, его сессию использует сама страница ВК; приложение cookies Chrome не читает.

Приложение получает результат одноразовой заявки самостоятельно. Сначала вызываются users.get и audio.get. Только успешный ответ музыкального метода разрешает сохранить новый токен в существующий AES-GCM/AndroidKeyStore конверт. При отказе или неизвестном ответе новый доступ не сохраняется, а ранее сохранённый токен остаётся на месте. Успех диспетчеризации браузера или status=2 сами по себе музыкальный доступ не подтверждают.

После подключения остаются ограничения 0.7.0: первые 10 треков/подборок, частичная выборка и одиночная загрузка. Массовая выгрузка, фоновая очередь, обмен super_app_token и обновление истёкшего токена не реализованы. ВК может потребовать повторного входа.

## Что подтверждено исходниками

- Официальный [VK ID Android SDK](https://github.com/VKCOM/vkid-android-sdk/blob/master/README.md) требует зарегистрированного приложения, client_id и client_secret. Само получение обычного VK ID токена не доказывает доступность audio.get.
- В официальной [схеме auth](https://github.com/VKCOM/vk-api-schema/blob/master/auth/methods.json) версии 5.199 нет публичного контракта используемых ниже методов.
- В [MusicX AuthCategory](https://github.com/Fooxboy/MusicX-WPF/blob/master/VkNet.AudioBypassService/Categories/AuthCategory.cs) есть веб-bootstrap /qr_auth, auth.getAuthCode и auth.checkAuthCode для публичного идентификатора веб-клиента 7913379. [Модели](https://github.com/Fooxboy/MusicX-WPF/blob/master/VkNet.AudioBypassService/Models/Auth/AuthCheckResponse.cs) различают ожидание, подтверждение, успешный ответ, истечение, access_token и super_app_token.
- В [AccountsWindowViewModel MusicX](https://github.com/Fooxboy/MusicX-WPF/blob/master/MusicX/ViewModels/Login/AccountsWindowViewModel.cs) ветка QR отключена с комментарием о невозможности получить Android-токен. Это существенное ограничение, а не доказанный готовый способ доступа к музыке.
- [Chrome](https://developer.chrome.com/docs/android/trusted-web-activity) не предоставляет host-приложению прямой доступ к cookies/localStorage. [Auth Tab](https://developer.chrome.com/docs/android/custom-tabs/guide-auth-tab) рассчитан на согласованный redirect; HTTPS-вариант требует Digital Asset Links владельца домена. Приложение не владеет доменом ВК.

Страницы документации dev.vk.com и id.vk.com при этой проверке не удалось прочитать доступным средством; это не заменено утверждением о якобы гарантированном публичном музыкальном OAuth.

## Выбранная проверяемая гипотеза

Веб-подтверждение устройства может вернуть пользовательский access_token, с которым ВК разрешит чтение audio.get. Пока это гипотеза: реальный вход и библиотека владельца здесь не проверены.

Реализован ограниченный эксперимент с веб-протоколом, без формы пароля, WebView, чужого Android client_secret, SafetyNet/GMS-эмуляции и обмена на токен официального Android-клиента. Код написан заново по наблюдаемым сообщениям протокола. Идентификатор 7913379 обозначает веб-клиент ВК, а не собственное зарегистрированное OAuth-приложение. ВК может отклонить запрос или выдать сессию с правами шире музыкальных; это явно написано перед кнопкой запуска.

## Ограничения и хранение

- Bootstrap и HTTP: только четыре заданных POST-метода на api.vk.com, платформенная проверка TLS, без cookies и HTTP-кэша. Автоматические редиректы запрещены. Одноразовая ссылка открывается только в Chrome после проверки точного HTTPS-узла.
- Тела ответов обрабатываются только в памяти, каждый JSON-ответ ограничен 1 МиБ и глубиной 32. HTML сайта больше не запрашивается. Cookies, токены, hash, verification и auth_url на диск и в лог не попадают.
- Опрос только после явного нажатия открытия браузера и при foreground Activity, не чаще одного раза в 5 секунд. Уже начатый запрос может закончиться после onPause. Подготовка заявки и ожидание её срока не являются фоновой массовой загрузкой.
- Срок заявки ограничен серверным значением и максимумом 5 минут; истечение также действует во время ожидания Chrome. Закрытие страницы/«Остановить» отменяет операцию и закрывает текущий запрос. Уход в Chrome сохраняет ожидание; после возвращения опрос продолжается.
- При убийстве процесса одноразовая заявка теряется, операция восстанавливается как прерванная. Токен до успешной проверки музыки не записывается.
- Неизвестный статус, неполная сессия, необходимость дополнительного пароля и неподдерживаемый super_app_token дают фиксированную ошибку. Не выполняется неявный обмен на другую клиентскую личность.
- В журнале: начало каждого фиксированного метода (anonymous / qr_bootstrap / create / poll), версия API, HTTP-код, размер и фиксированная категория MIME. native_auth_response_shape содержит только тип тела, версию парсера, успех конверта и наличие известных полей; значения и произвольные имена полей исключены. native_auth_session фиксирует формат срока и его оставшуюся длительность. Также сохраняются числовой status, фиксированный token_kind, коды ошибок, foreground и способ обнаружения. Значения секретов, URL подтверждения, тела запросов/ответов и исходные исключения не сохраняются.

## Проверки и критерии результата

JVM использует синтетические ответы и перехваченные HTTP-вызовы: строгий разбор, границы URL, истечение, отмена, пауза в фоне, отсутствие секретов в диагностике. Android-тесты проверяют страницы/возврат/пересоздание Activity, настоящие Keystore и сохранение старого доступа при отказе audio.get, с подставными провайдерами сети и браузера. Эти тесты не являются успешной авторизацией на ВК.

Для реальной проверки нужны события: anonymous → qr_bootstrap → create → READY → browser dispatch → возврат Activity → poll status=2 с access_token → успешные users.get/audio.get → CONNECTED. Если последнее не получено, подключение не объявляется успешным. По реальному логу следующий шаг определяется отдельно: изменение bootstrap, подтверждение в браузере, другой тип токена либо отказ музыкального API.

Опциональная проверка именно нативного Kotlin-клиента: VKM_PUBLIC_BOOTSTRAP_PROBE=1 ./gradlew testDebugUnitTest --tests '*PublicDeviceAuthProbeTest'. Она создаёт только неподтверждённую анонимную заявку и проверяет статус ожидания; по умолчанию пропущена, чтобы обычные проверки не зависели от ВК. Вывод содержит только производственные безопасные метаданные. Регрессионные JVM-тесты проверяют последовательность POST, отказ до следующего этапа при HTML, Unix/относительный срок, границы доверенного URL и отсутствие секретов.
