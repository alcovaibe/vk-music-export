## Подтверждено кодом 0.8.1

- Первая ссылка отправляется ACTION_VIEW с setPackage("com.android.chrome"). Приложение не выбирает Samsung Internet. Это ограничение первого Intent, а не контроль всех следующих переходов страницы и Android.
- Дополнительное подтверждение не реализовано: DeviceAuthProtocol.poll принимает 0, 1, 200, 4 и 2; остальные статусы превращает в RESPONSE. NativeMusicPanel не имеет поля для кода привязки, а DeviceAuthApi не имеет операции его подтверждения.
- Успех входа в браузере не подтверждает соединение экспортёра. Для CONNECTED нужны статус авторизации, успешные users.get/audio.get и запись проверенного доступа.
- Существующий журнал не наблюдает дальнейшие страницы, диалоги, Intent-переходы, cookies и ошибки браузеров.

## Что известно из других реализаций

В [типах vk-desktop](https://github.com/danyadev/vk-desktop/blob/0b69f0280988f219770358b3c06f4072de497305/src/services/contracts/api/methods/Auth.ts) статус 3 означает отказ, 5 — запрос дополнительной проверки. auth.validateAuthCode принимает auth_hash и validation_code; ответ различает принятый/неверный код и истёкшую сессию. [Координатор](https://github.com/danyadev/vk-desktop/blob/0b69f0280988f219770358b3c06f4072de497305/src/services/QrCodeAuth.ts) показывает отдельное состояние VerificationRequested и отправляет код по действующей заявке.

Похожий шаг есть в [Kittytune](https://github.com/alan7383/kittytune/blob/4a78611667378755d1accc113fdd071bfc9e384f/app/src/main/java/com/alananasss/kittytune/data/vk/VkQrAuthManager.kt). Это первичные исходники сторонних клиентов, а не публичная гарантия контракта ВК. Из них нельзя заключить, что показанный владельцу код точно относится к статусу 5.

Официальная [документация Chrome](https://developer.chrome.com/docs/android/intents) описывает запуск внешних приложений через Intent-ссылки и fallback URL. Это возможный механизм переключения приложения; на конкретном телефоне он ещё не установлен.

Записаны только фиксированные стадии, HTTP-метаданные, очищенные узлы/пути и классификации элементов. Значения query, кода, cookies и страницы не сохранены. Это desktop Chromium с мобильными параметрами, не Samsung Galaxy, не настоящий Android Intent resolver и не профиль владельца. Проверка не воспроизводит дополнительное поведение после входа и не опровергает переключение браузера на телефоне.

## Гипотезы и необходимые данные

1. ВК показал код привязки, предназначенный для ввода инициатору заявки. Это согласуется с отсутствующим шагом status=5, но требует текста инструкции рядом с кодом либо native_auth_poll_result со status=5.
2. Браузер сменился при последующем внешнем переходе, открытии ссылки другим приложением или выборе системного обработчика. Нужны очищенные метаданные разрешения первой ссылки и описание следующего экрана. Системный браузер по умолчанию пока не известен; объявлять его причиной нельзя.
3. Запрет относится к конкретной заявке, состоянию подтверждения, ограничению сервера или другому этапу. Без точного текста/стадии/числового ответа нельзя утверждать бан аккаунта, временную блокировку, ошибку VPN или гарантированное исправление сменой браузера.

Ручное описание этой записи больше не требуется: ключевые надписи прочитаны. Для проверки серверной причины нужен числовой status и стадия из штатных событий native_auth_poll_result/native_auth_failed той же попытки. Код, пароль, токены и полный одноразовый URL не нужны. В разобранной записи подтверждён AUTH_RESPONSE приложения; отдельный серверный текст запрета ею не установлен.

## План исправления с критериями

1. Различить код привязки и SMS/OTP входа. Пароли и SMS/OTP остаются на стороне ВК. Если сервер требует именно код привязки для инициатора, добавить отдельное состояние и понятный защищённый экран только для этой заявки, а не общее поле для любых кодов.
2. Обрабатывать status=3 отдельно как отказ; status=5 — как запрос дополнительного подтверждения, а не неизвестный формат. Проверить параметры auth.validateAuthCode на актуальном протоколе. Неверный код не должен автоматически создавать новую заявку; срок, отмена и отказ должны прекращать текущую операцию.
3. Код привязки держать только в памяти, без saved state, журналирования, автокопирования и автоматического чтения буфера. Очищать при отправке/закрытии. Состояние ожидания и срок заявки проверять монотонно. При неуспехе сохранять прежний музыкальный доступ.
4. Добавить безопасную диагностику первоначального обработчика/браузера. Проверить возможность Chrome Custom Tabs с настоящим профилем; не обещать, что выбор первого браузера запрещает все последующие внешние Intent страницы. Не менять системный браузер пользователя автоматически.
5. Проверить последовательность на синтетических ответах и Android UI: status=5, ввод/отмена, неверный/принятый код, истечение, status=3, пересоздание и прерывание процесса; отсутствие кода в JSON и сохранение старого доступа.
6. Реальный критерий: понятная инструкция и верный этап для кода, подтверждение своей заявки, status=2 с поддерживаемым доступом, успешные users.get/audio.get, CONNECTED. Только после этого объявлять музыкальный вход рабочим. Получение super_app_token требует отдельного обоснованного этапа обмена; оно не заменяет проверку музыки.

При разборе записи исправления APK не выпускались. Подтверждены пробел реализации, BUSY в начале записи, экран запроса нового устройства и AUTH_RESPONSE после возврата. Числовой статус, точное назначение кода и причина сообщённого ранее запрета по самой записи остаются открытыми.

## Реализация исправления 0.8.2

Добавлены status=3/5, строгий auth.validateAuthCode, отдельный защищённый экран только по серверному запросу кода, повтор неверного кода в той же заявке, ожидание status=2 после принятия кода и прежняя обязательная проверка музыки до записи доступа. Начальная навигация использует Chrome Custom Tabs с обычным профилем и отключённой отправкой редиректов обработчику по умолчанию. Отмена удерживает busy до окончания очистки; другая Activity ждёт освобождения mutex, а не получает BUSY.

Регрессионные тесты охватывают запрос/отказ/срок, неверный и принятый код, ожидание окончательного подтверждения, отмену, фон, защищённый экран, очистку поля при восстановлении состояния, Chrome Intent и сохранение прежнего Keystore-доступа при отказе музыки. Эти проверки с подставными ответами не являются реальным входом владельца. [Описание текущего протокола и ограничений](BROWSER-AUTH.md).
