# Поиск обложки для сохранённой записи — 0.9.16

Песня, удалённая из «Моей музыки» ВК, может остаться доступной в других записях каталога. Пустой audio.getById по сохранённому ID не означает, что песни вообще нет в ВК. В результатах обработки старых файлов этот случай называется «Не найдены по сохранённому ID». У каждой такой записи есть «Найти обложку в ВК». Поиск запускается пользователем; обычная обработка не ищет и не выбирает замену автоматически.

## Нижняя панель

1. Проверяется конкретная сохранённая запись SQLite и целостность её локального файла. В строке поиска подставляются исполнитель и название. Запрос можно изменить или заменить полной ссылкой на песню.
2. «Найти» вызывает audio.search с q, count=20, offset, auto_complete=0, search_own=0, sort=2. Доступны страницы до первых 100 результатов; для остальных нужно уточнить запрос. Чтение музыкальной библиотеки и подборок остаётся страницами по 100.
3. Варианты показывают название, исполнителя, длительность и альбом, если он есть. Нет обложки, ограниченная запись и небезопасные данные картинки обозначаются отдельно. Автоматического выбора первого совпадения нет.
4. «Посмотреть обложку» загружает только изображения выбранной записи. Используются thumb/album.thumb из самого ответа поиска: повторный запрос старого ID не требуется. Варианты размеров после 404/410, лимиты времени/байтов/пикселей, HTTPS/домены и отсутствие API-секретов у CDN сохраняются.
5. Отдельный экран внутри нижней панели показывает картинку, исходный файл и найденную запись. Разница длительности выделена; совпадение аудиозаписей не заявляется. «Добавить эту обложку к файлу» даёт отдельное одноразовое согласие. «Назад к вариантам» ничего не записывает.

Аудио не скачивается для сравнения или повторного сохранения. Выбор принадлежит пользователю: совпадения названий, исполнителей и длительности не доказывают одинаковое исполнение, ремикс или издание. Кандидат служит только источником картинки. Сохранённый NativeTrack/ID, имя, папка и URI не заменяются; запись в профиль ВК не добавляется. Методы audio.add, audio.delete и изменения плейлистов в этом пути отсутствуют.

## Полная ссылка вместо поиска

Поддержаны HTTPS-ссылки vk.com, m.vk.com, music.vk.com и соответствующие vk.ru:

- https://vk.com/audio123_456
- https://m.vk.com/audio-123_456
- https://vk.com/music?z=audio123_456

Ссылка разбирается локально. Нужен ненулевой owner_id (включая отрицательный для сообщества) и положительный audio_id в диапазоне Long. Затем выполняется только фиксированный audio.getById на api.vk.com; ответ должен содержать ровно этот ID. Исходный URL не открывается HTTP-клиентом и не используется для загрузки картинки. Чужие домены, HTTP, userinfo, нестандартные порты, фрагменты, короткие ссылки и ссылки на подборки отклоняются до API-запроса. Короткую ссылку сначала нужно открыть в своём клиенте ВК и скопировать полную. Произвольные URL изображений не принимаются.

Если ВК не разрешает audio.search текущему доступу, панель объясняет отказ и предлагает попробовать полную ссылку. Успех audio.getById по другой ссылке также не гарантируется: права определяет ВК. Пароли и SMS по-прежнему вводятся только на стороне ВК.

## Запись и границы

Выбор и адреса существуют только в памяти ViewModel. Результаты поиска действуют 10 минут, просмотренная картинка — 5 минут. Изменение запроса, закрытие панели, другая музыкальная операция, уход с музыкального экрана или в фон сбрасывают ожидающий выбор. Смена реквизитов доступа требует нового поиска. Отложенные результаты старой операции не восстанавливают закрытую панель. Отмена во время ожидания общего mutex освобождает состояние операции.

Запись использует прежний ArtworkRepair: проверка владельца/папки/размера/SHA-256, резервная копия, журнал, неизменность MP3 payload/M4A mdat, проверка встроенной картинки и обновление хеша SQLite. Непосредственно перед изменением файла повторно проверяются поколение операции, активность приложения и тот же доступ. При отказе этого последнего барьера журнал восстанавливается и исходник остаётся целым. Существующая обложка не заменяется. Готовые файлы по-прежнему пропускаются до чтения при пакетном повторе; очищенная история не возвращается.

Запись взаимно исключается с UIDT через прежний общий механизм. Поиск и просмотр не создают очередь скачивания. Имена, запросы поиска, ссылки, ID треков, изображения, токены и тела ответов не попадают в JSON или публичные файлы. События audio_artwork_lookup и audio_artwork_lookup_candidate содержат случайный operation_id, этап, счётчики, фиксированные коды и HTTP-статусы.

## Проверка и источники

Контракт audio.search сверялся с первичным исходником [AIMP VK / TVKService.AudioSearch](https://github.com/ArtemIzmaylov/aimp_VK/blob/main/AIMP.VK.Core.pas) и [исторической документацией VK.NET](https://vknet.github.io/vk/audio/search/). Они не подтверждают доступность метода для нашего токена сейчас.

JVM-сценарии проверяют параметры чтения, строгий разбор ссылок/ответов, отсутствие автоматического выбора/записи, отмену, смену доступа, срок и одноразовость согласия. Эмуляторы проверяют подтверждение/возврат, точную связь кнопки с файлом, настоящие MP3/M4A/MediaStore с сохранением аудиобайтов и старого ID, журнал при отказе перед записью и полный путь ViewModel с уходом в фон. Сеть синтетическая. Реальный поиск, права токена и подбор обложек к пяти записям владельца ещё не проверены.
