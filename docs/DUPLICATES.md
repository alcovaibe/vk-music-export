# Дубликаты в «Моей музыке» ВК — 0.9.18

«Очистить дубликаты» находится сразу после «Скачать всю мою музыку», только во вкладке библиотеки. Кнопка открывает нижнюю панель; поиск начинается отдельным нажатием. До запуска панель предупреждает об интернете, временном скачивании и свободном месте. Поиск не удаляет записи. Свернутую панель можно снова открыть через «Дубликаты: процесс и результат»; с 0.9.18 сворачивание и уход с музыкального экрана не останавливают поиск и временную загрузку. Поиск работает в отдельной UIDT-задаче Android, а не в scope ViewModel. Проверка перед удалением/само удаление по-прежнему относятся к активному приложению. Панель и согласия живут в ViewModel. Завершённые проверки SHA-256 сохраняются на диске и переживают остановку, уход в фон, пересоздание Activity и перезапуск процесса. Кнопка «Продолжить проверку» запускает новое чтение библиотеки и повторно использует подходящие результаты; согласия на удаление не восстанавливаются.

## Фон и уведомление

Поиск запускается нажатием в видимом приложении. Отдельные job/notification/channel не смешиваются с очередью обычного скачивания. Уведомление показывает этап, общий прогресс, текущий трек, полученные байты и число сохранённых проверок; видимость PRIVATE. Нажатие открывает музыкальный экран и панель процесса/результата. «Пауза» относится к конкретному случайному ID запуска: старое уведомление не отменяет новый поиск. Разрешение уведомлений нужно для показа в шторке; существующая кнопка разрешения сохранена.

Поиск переживает закрытие Activity. Android может остановить UIDT, при force-stop процесс может погибнуть без callback. Незавершённый трек не считается проверенным. Атомарный duplicate-job.json хранит случайный ID запуска, credential_id и фазу без токена, cookies, URL и согласий; SHA-256 хранятся отдельно в прежнем кэше. При перезапуске процесса доступно явное продолжение. Если Android повторно запустит уже принятую задачу и сохранённый credential_id совпадает, задача может продолжить с кэшем; после смены ID в другом процессе требуется явное продолжение, поскольку цепочку автопродления того процесса доказать нельзя. Итоговый список дубликатов и согласия между процессами не восстанавливаются — выполняется новое чтение библиотеки с готовыми SHA-256.

Одновременно с этим поиском нельзя начать другую очередь загрузки, запись обложек/файлов или смену доступа. Общий mutex файловых операций и проверка состояния исключают гонку запуска. Проверка перед удалением не запускается в JobService, кэш для неё не читается; перед каждым удалением обе записи снова загружаются и проверяются с отдельным одноразовым согласием в активном приложении.

Платформа: [Android UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt). Реальные фоновые ограничения телефона, длительная работа с ВК и продолжение после системной остановки на аккаунте владельца ещё требуют проверки. CI использует локальный звук и синтетический API.

## Как подтверждается совпадение

1. Библиотека читается полностью страницами по 100, с прежними проверками количества/повторения страниц. Переходы между страницами имеют паузу 400 мс; это не гарантия отсутствия ограничений ВК.
2. Кандидаты группируются по исполнителю и названию: NFKC, свёртка пробелов, регистр ROOT. Пунктуация, remix, feat и прочие части имени не удаляются. Разные ID одного имени сами по себе не являются доказанными копиями.
3. Только записи из таких групп временно загружаются через существующий AudioTransfer. Media3 выделяет исходные аудиосэмплы без перекодирования; после нормализации считаются SHA-256 MP3 payload либо подпись M4A v2: mdat, конфигурация декодера, временная шкала, размеры/размещение сэмплов. Текстовые теги/обложки не участвуют. Сопоставляется пара формат + SHA-256. Разные битрейты, кодеки и исполнения могут остаться разными даже при похожем звучании: аудиоотпечатка нет.
4. Библиотека перечитывается целиком. Изменение списка во время проверки требует нового поиска. В каждой подтверждённой группе первая запись фиксируется как оставляемая, остальные N−1 предлагаются по отдельности.

ВК не предоставляет SHA-256 аудиоданных: проверка может использовать большой объём трафика и времени. Не скачиваются треки с уникальными названиями/исполнителями. Незавершённая загрузка находится в cacheDir/duplicate-check и удаляется при отмене/ошибке/закрытии проверяющего объекта; после аварийной гибели процесса остаток убирается при следующем запуске этого объекта. После успешной проверки полный аудиофайл удаляется. Атомарный checks.json v2 сохраняет только формат, версию алгоритма и контрольную подпись; старые квитанции v1 не принимаются. Ключ — SHA-256 метаданных NativeTrack, owner_id и подпись упорядоченного снимка библиотеки; токены/cookies/URL отсутствуют. Срок квитанций — 24 часа, до 20 000 записей. Старые оставшиеся MP3/M4A из постоянного кэша удаляются при следующем начале проверки; повтор использует квитанции, без хранения 256 МиБ ненужного аудио.

## Продолжение и срок хранения

- Результат сохраняется только после полной загрузки, Media3-проверки и расчёта SHA-256 payload. Частичные загрузки, ошибки и отменённая обработка не считаются готовыми. Незавершённый трек загружается заново целиком: HTTP Range и возобновления HLS по сегментам нет.
- Перед использованием результатов библиотека полностью читается заново. Аккаунт и полный упорядоченный снимок, включая ID, названия, исполнителей, длительности, ограничения и альбомы, должны совпасть. Любое изменение сбрасывает результаты; завершение поиска также требует неизменности библиотеки. После удаления дубликатов следующий поиск начнётся с новым снимком.
- Срок снимка — 24 часа с начала, максимум 20 000 проверок; после лимита вытесняются старые результаты. Аудиокопии занимают не более 256 МиБ: старые копии удаляются при превышении. Готовый проверенный хеш остаётся до срока/смены снимка, даже если аудиокопия вытеснена, поэтому повторное скачивание для поиска не требуется. Это кэш результата проверки, а не копия музыки для прослушивания.
- Истёкший, повреждённый или чужой снимок отбрасывается. Удаление сохранённого доступа через приложение очищает этот кэш. При новом входе кэш может использоваться только после полного чтения той же библиотеки того же аккаунта. Подтверждения на удаление из старого запуска никогда не восстанавливаются.
- Панель показывает число сохранённых проверок и повторно использованных результатов. Сеть и доступ восстанавливаются отдельно; продолжение запускает пользователь. Уже готовые проверки не загружают аудио повторно. Уникальные названия/исполнители по-прежнему не скачиваются.

## Продление доступа во время поиска

Прежняя проверка UI фиксировала credential_id в начале всей операции. Автоматическое продление сохраняет новый credential_id; следующий локальный guard выдавал ACCESS, даже если новый токен уже проверен через users.get/audio.get и успешно сохранён. Длительный поиск временно загружает все совпадения и дольше обычной отдельной загрузки пересекает границу продления. UIDT-очередь получает текущий доступ перед API-запросами и не имеет именно этого guard всей проверки дубликатов.

Поиск теперь следует цепочке только успешных проверенных автопродлений общего MusicSessionManager. Произвольный новый вход, другой аккаунт и удаление доступа прерывают старое чтение. Готовый отчёт связан с текущим credential_id. Проверка перед удалением по-прежнему требует точного совпадения доступа: автоматического переноса согласия и повтора мутации нет.

Это воспроизводимая ошибка кода, но один скриншот владельца не доказывает её как единственную причину конкретной остановки. Настоящий отказ ВК/code 5, запрет метода и неудачное продление также возможны. В JSON ошибки поиска добавлены фиксированный этап, локальная смена доступа или отказ проверки/запроса, vk_code и счётчики сохранённого/повторно использованного. Имена, ID треков, хеши и адреса не добавляются. Сообщение панели больше не утверждает отказ сервера, когда известен лишь сбой проверки доступа.

## Подтверждение каждого удаления

В списке видны количество лишних записей, удалённых, пропущенных и ожидающих решения, название, исполнитель, точные ID и оставляемая запись. Неподтверждённые кандидаты имеют отдельную причину. Для выбранной записи открывается подтверждение в той же нижней панели: что удаляем и что оставляем. Кнопка удаления имеет красную рамку и текст. Отмена ничего не отправляет. «Пропустить» оставляет запись; общего подтверждения/удаления всех дубликатов нет.

Каждое согласие одноразовое и связано с аккаунтом, текущими зашифрованными реквизитами доступа и конкретной парой записей. До запроса заново читается вся библиотека, проверяется единственное присутствие обоих точных ID и неизменность их метаданных. Кэш поиска перед удалением не читается. Обе записи ещё раз временно скачиваются и сверяются с подтверждённым SHA-256, после чего библиотека перечитывается повторно. Непосредственно перед запросом проверяются поколение операции, доступ и активное приложение. Запрос выполняет существующий клиент: users.get тем же токеном, затем один POST audio.delete. Автоматического повтора мутации при сетевой ошибке или обновлении токена нет. Числовой response=1 означает подтверждение ВК; после него статус меняется только у выбранного дубликата. Для следующего требуется новое отдельное подтверждение.

Чтения и удаление на сервере не образуют атомарную транзакцию: внешнее изменение в последнем промежутке между проверкой и запросом полностью исключить нельзя. При неопределённом исходе операция блокируется, запись отмечается как неподтверждённая; требуется новый поиск. Поздний результат не применяет старое согласие к новому входу. Выход, новый вход, другое действие и уход в фон сбрасывают ожидающее подтверждение. Ожидание общего mutex также корректно отменяется.

## Границы

- Поддерживаются только положительные owner_id текущего профиля, как в существующем одиночном удалении. Чужие/групповые owner_id показываются как неподдерживаемые; права токена не обходятся.
- Повторения одного и того же ID на нескольких позициях не удаляются: audio.delete адресует ID, а не конкретную позицию, поэтому сохранение одной позиции этим запросом нельзя гарантировать.
- Активная, ожидающая или незавершённая очередь скачивания блокирует поиск/удаление. Общие mutex исключают параллельные операции приложения с этим поиском и проверкой перед удалением.
- Локальные аудиофайлы, история, связи сохранённых файлов, обложки и очередь не удаляются и не переписываются. Отдельная корзина трека [по-прежнему требует проверенную локальную копию](LIBRARY-REMOVAL.md); поиск дубликатов вместо этого проверяет остающуюся запись в ВК.
- Старые страницы библиотеки сбрасываются перед мутацией. После работы нужно нажать «Проверить музыку», чтобы прочитать актуальные страницы. Влияние удаления из библиотеки на связанные списки определяет сервер ВК; операции удаления из плейлиста не вызываются.
- Диагностика содержит только случайный ID поиска, счётчики, фиксированные коды и исходы. В неё не добавляются имена, ID треков, URL, SHA-256 или токены.

JVM-проверки используют синтетический API и хеши; инструментальные — также локальные MP3, настоящие Media3 и UI подтверждений. Владелец сообщил об остановках реального поиска; новое продолжение после продления и audio.delete на аккаунте владельца не проверены: зелёный CI не подтверждает права токена и реальный результат ВК.
