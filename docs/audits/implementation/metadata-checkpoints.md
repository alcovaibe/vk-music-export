# F07: отдельные цели, курсор и ошибки проверки метаданных

Дата: 4 ноября 2026. База: `470d13e43277492e91a991b9e536a5f04e90b521`.
Ветка: `fix/audit-stage0-release-delivery-20261104`.

## Хранение и совместимость

SQLite переводится с v3 на v4 добавлением трёх таблиц: `metadata_runs` (runId, число/хеш целей и небольшой курсор), `metadata_targets` (неизменные цели по owner + ordinal) и `metadata_issues` (ошибки по owner + ordinal). Существующие tasks/files/meta/directories/source_failures и идентификаторы/URI не удаляются. Пути миграции v1/v2 сохранены и расширены до v4; проверки версии в тестах и signed-upgrade скрипте обновлены.

Старый `meta[track-metadata-run:<owner>]` переносится лениво при первом чтении владельца в одной транзакции. Исходный ключ удаляется только после успешной записи нового представления. Ошибка формата, слишком большая запись, abort или SQLiteFull сохраняют старую копию. Другие аккаунты и неизвестные ключи не затрагиваются.

Legacy JSON читается блоками по 64 KiB как BLOB и затем целиком декодируется строго как UTF-8. Это позволяет переносить снимки больше одного окна курсора, в том числе с кириллицей на границе блока. Перенос ограничен 64 MiB; более крупный старый checkpoint остаётся без изменений и возвращает STORAGE. Размер отдельной новой target/issue JSON-строки ограничен 64 KiB; превышение не обрезается и не выдаётся за успешный импорт. [CursorWindow](https://developer.android.com/reference/kotlin/android/database/CursorWindow) имеет ограниченный размер, поэтому цели хранятся строками, а не одной многомегабайтной ячейкой.

## Запись прогресса

TrackMetadataBatch выполняет один полный save при начале/возобновлении, затем вызывает `metadataProgress(before, after)`. Список целей остаётся тем же объектом/порядком; по каждому элементу обновляется только маленький JSON курсора и, при необходимости, добавляется одна ошибка. Они фиксируются атомарно. Ошибка авторизации/сети сохраняет error без увеличения next. Ожидаемые runId и предыдущий курсор защищают от опоздавшего или повторного writer; замена списка/порядка внутри того же runId отвергается.

Полный save проверяет хеш целей, но не переписывает их для того же runId. Ручное исправление ошибки обновляет только изменённые issue rows; неизменные строки ошибок тоже не перезаписываются. Чтение состояния UI восстанавливает курсор/ошибки без десериализации всех целей. Полный список загружается для запуска batch и проверки хеша.

MaintenanceRuntime хранит ссылку metadataOwner на авторитетное состояние SQLite. Привязанный список ошибок не сериализуется повторно в `maintenance.json`, но остаётся в памяти UI и восстанавливается из БД. Старые maintenance-файлы без этой ссылки сохраняют прежний формат до привязки к известному checkpoint. Остальные операции обслуживания/уведомления и их очереди сохраняются.

Это устраняет квадратичную сериализацию/запись целей после каждого трека. Это не обещание линейного времени всей обработки: VK, проверка файлов/плейлистов и копирование списка ошибок в UI имеют отдельную стоимость. F08 (receipt cache), F09–F11 и реальные Macrobenchmark/профилирование остаются отдельными задачами.

## Проверки

Добавлены три JVM-регрессии: один полный снимок + адресные дельты, восстановление после ошибки записи дельты без пропуска текущего трека и старый JSON без runId.

Добавлены семь инструментальных сценариев, каждое точное имя обязательно для verifier на API29–37:

- v3 → v4 с сохранением очереди, реального MP3, старого курсора/ошибок, reopen и продолжением без запроса готового файла;
- abort импорта с сохранением единственной legacy-копии, malformed/oversized данные и последующий успешный retry;
- атомарный rollback ошибки/курсора, отклонение повторного и устаревшего writer;
- настоящий SQLiteFullException через ограничение `max_page_count` изолированной БД, сохранность предыдущего состояния после reopen;
- неизменность целей, ручное разрешение ошибки, изоляция аккаунтов и отказ при повреждении snapshot;
- компактный maintenance-журнал и восстановление issues из БД;
- замеры checkpoint для 100/4500/20000 целей и перенос legacy JSON больше 2 MiB с кириллицей.

SQLiteFull здесь означает реальное исчерпание разрешённых страниц тестовой БД; весь накопитель устройства не заполняется. Abort транзакции и reopen не выдаются за физическое отключение питания.

## Методика производительности

Изолированная Android SQLite в CI-эмуляторе, без VK и сканирования медиа. Замеряются initial snapshot, N отдельных checkpoint-транзакций (включая p95) и restore после закрытия БД. SQL-триггеры считают записанные UTF-8 payload bytes и число записей: каждая цель должна быть записана ровно один раз, число progress writes — N+1, размер progress payload ограничен константой в тесте. Workload без issue rows; ошибки/ручные изменения проверяются функциональными сценариями отдельно.

Это логические payload bytes, не физические байты WAL/SSD и не скорость полного музыкального экспорта. `legacy_targets_min_bytes_estimate = target_payload_bytes × (N+1)` — расчёт нижней границы прежней сериализации целей, не измерение старого времени работы. Времена с измерительными триггерами не объявляются пользовательской задержкой UI.

JSON-результаты каждого API сохраняются в `interface-benchmarks/` вместе с Actions reports. Конкретные измерения нужно читать по SHA этого изменения. Исторические серверные микрозамеры из аудита не подменяют новые Android-измерения.
