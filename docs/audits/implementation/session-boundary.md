# F01: граница аккаунта при разрешении доступа

Рабочая ветка: `fix/audit-stage0-release-delivery-20261104`.
База этого изменения: `3ce3b32924d229be0e4a4421b68a8da8cdddfff4`.

## Изменение

`MusicSessionManager.request()` теперь получает доступ через `continueRead(supplied)`, который проверяет исходный `readSessionId` и известный `accountId` до разрешения и после него. Совпадающий token или credentialId не разрешает подстановку нового независимого входа. Проверенное продление той же сессии остаётся допустимым; проверка владельца renewal не удалена.

`resolve()` дополнительно принимает ожидаемый доступ. Он проверяет каждое чтение хранилища до обновления/публикации состояния, включая рекурсивный путь, когда параллельный запрос уже обновил токен после ошибки 5. Повторный request block также получает доступ только после проверки исходной границы. Сеть самого request block остаётся вне Mutex; существующий single-flight продления и CAS записи сохранены. Первичная проверка несохранённого кандидата по-прежнему использует его собственный токен.

Это предотвращает подстановку нового аккаунта в запрос старой сессии. Это не обещание отзыва уже отправленного сетевого запроса и не полная реализация read lease для всех операций UI. F22 (ручной поиск обложек) требует отдельного изменения и пока открыт.

## Регрессионные сценарии

В `MusicSessionBoundaryTest` добавлены восемь JVM-тестов без sleep и реального VK-аккаунта. Хранилище возвращает разные значения на точно заданных чтениях:

- вход B или новый независимый вход A между предварительной проверкой и resolve;
- новый вход с повторно выданным таким же token или credentialId;
- другой accountId при ошибочно сохранённых тех же идентификаторах сессии;
- logout между чтениями;
- уже заменённая сессия до resolve;
- допустимая проверенная ротация того же readSessionId;
- смена входа внутри рекурсивного ACCESS retry и допустимая ротация на этом же пути;
- несохранённый pairing candidate рядом со старым сохранённым аккаунтом.

Существующие MusicSessionTest проверяют single-flight, отмену, CAS после logout/нового входа, ровно один retry, ограничения повторов, owner verification и 80 последовательных продлений. Исторический файл ProposedTest в аудите не изменён и не объявлен выполненным сам по себе.

## Проверки и выпуск

Локальный Gradle запуск `testDebugUnitTest --tests '*MusicSession*'` остановился до конфигурации проекта: загрузка Gradle 9.8.2 — `Network is unreachable`. Это не результат Kotlin-компиляции и не успешный тест. Для выполнения JVM/Lint/R8 и API29–37 push в `fix/**` теперь запускает существующий полный Android workflow; условия release job не расширены. Проверки только читают исходники новой ветки, публикация без отдельного запроса не происходит.

Результат конкретного CI нужно читать по SHA коммита этого изменения. Успех Python или канального workflow не заменяет исполнение Kotlin-тестов. Main, версия приложения, Releases, канал main и фактическая ручная приёмка не изменяются.
