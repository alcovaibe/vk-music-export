# Массовая загрузка: подготовка очереди без лишних проходов

Ветка: `fix/audit-stage0-release-delivery-20261104`.
Основа: `7ad7adabe7c9011233d4fce4fef83f7b3d42cc2c`.
Main, Releases, схема БД и существующие пользовательские файлы не изменяются.

## Что изменено

Ранее `prepare()` повторно читал библиотеку или каталог. Для категории он
сначала запускал `downloadedCatalog()` по всему каталогу, включая другую
категорию, а затем ещё раз получал содержимое оставшихся источников.

Планирование вынесено в `ExportPreparation`. Оно использует полные результаты
недавнего анализа, чтения открытой подборки и фоновой проверки сохранённых
подборок. Если подходящего результата нет, выбранный источник читается один
раз с прежней pagination и обработкой ошибок. Подготовка альбомов не читает
плейлисты и наоборот. Режим группировки своей библиотеки по альбомам использует
тот же снимок библиотеки, без дополнительного чтения каталога.

`completedPrepared()` проверяет локально только уже запланированные источники.
Порядок/членство берутся из готового плана, повторных VK-запросов нет; ключи
задач тоже не вычисляются второй раз. Полностью сохранённая выбранная подборка
пропускается только после проверки реальных файлов и M3U8. Старая отметка
`hiddenCatalog` сама по себе не является доказательством сохранности. Для
остальных задач остаются прежние проверки `SavedAudioReuse` и движка.

## Снимки и их ограничения

`ExportReadCache` хранится только в памяти текущей ViewModel. Срок пригодности
полного результата — 60 секунд от завершения чтения; граница включительно
считается истечением. Кэш ограничен 40 000 позиций и 64 страницами источников,
вытеснение LRU. Здесь «страница источника» означает полный результат pagination
одного источника, а не отдельный HTTP-ответ на 100 записей. Каталог ограничен
20 000 описаниями подборок. Большой источник сверх лимита читается обычным
путём и не удерживается дополнительно в кэше.

Снимки привязаны к владельцу, readSessionId и поколению анализа. Частичные
результаты не записываются. Отмена не превращает неполный список в полный.
Уже завершённые источники отменённой подготовки можно использовать при повторе
в пределах срока; незавершённый источник читается сначала.

Явный анализ, вход/выход и попытки удаления музыки из VK сбрасывают снимки.
Обновление каталога сбрасывает каталог и его страницы. Полученное новое
описание источника с другим количеством, именем, типом, original ID, access key
или признаками доступности инвалидирует прежнюю страницу. Отсутствие источника
в неполном каталоге не считается доказательством удаления. Неполный album filter
не превращается в полный каталог альбомов.

Это подготовка **по недавнему анализированному снимку**, а не обещание атомарного
снимка всей текущей музыки VK. Изменение состава с прежним количеством позиций
на сервере невозможно доказать без нового чтения или поддерживаемой ревизии
провайдера. TTL сам по себе этого не доказывает. Явное обновление получает новые
данные; точная доступность каждой записи при сетевом скачивании по-прежнему
проверяется существующим resolve по ID. UI сообщает, когда очередь использовала
результаты последнего анализа.

В кэше нет токенов, signed media URL, аудиофайлов и вердиктов целостности файлов.
Metadata/access key из ответа VK не записываются на диск этим механизмом и
не выводятся в диагностику. Перед планированием проверяется реальный владелец
аккаунта; перед записью очереди повторно проверяется сессия. Новый вход даже того
же владельца не использует старое состояние UI. Разрешённое продление прежней
read session остаётся допустимым.

## Проверки

- 18 новых JVM-сценариев: ограничения и LRU, TTL и ход часов назад, fence старых
  писателей, частичные данные, изменённое описание, источники с повторными
  вхождениями, группировка альбомов, отмена, явные ошибки недоступных источников.
- Для 100/4500/20000 треков тест планирования требует ноль повторных запросов
  страниц при пригодном полном снимке и сохранение количества/порядка задач.
- На холодном тестовом каталоге с подборками 101 + 1 трек и посторонним альбомом
  требуется три запроса страниц выбранных плейлистов и ноль запросов альбома.
  Повтор по пригодным снимкам не должен читать ни каталог, ни страницы.
- Семь новых instrumentation-сценариев проверяют настоящую ViewModel и SQLite:
  подготовку из анализа, открытую подборку, чтение только выбранной категории,
  истечение срока, отмену/повтор, новый вход и logout во время чтения. Подменён
  только запуск фонового сервиса; существующие тесты движка отдельно проверяют
  реальные файлы, дедупликацию, целостность и восстановление очереди.
- CI проверяет наличие каждого из семи новых Android-сценариев в XML: их
  отсутствие или пропуск не может дать успешную матрицу.
- Существующий CatalogRefreshDeviceTest сохраняет требование: полностью
  сохранённый альбом не создаёт новую очередь; изменённый/пропавший файл не
  позволяет скрыть подборку. Старые проверки не ослаблены.
- Локально: 127 Python-тестов прошли за 3.042 секунды, `git diff --check` прошёл.
  Запуск Gradle остановился до компиляции на скачивании дистрибутива
  (`Network is unreachable`). JVM/Android-результаты требуют отдельного
  подтверждения в Actions для точного SHA; они заранее не объявляются успешными.

Количество запросов выше — проверяемые сценарии с fake API, не измерение сети
VK или скорости телефона. Время реального скачивания, настоящий VK-аккаунт,
физическое устройство и длительный прогон с обрывами здесь не проверены.

F09–F11 остаются отдельными задачами: чтение ошибок, индексы URI и обход
MediaStore. Полный local `savedFiles()` для проверки выбранных источников ещё
существует. Также не устранены повторное чтение при открытии подборок,
проверки каталога после завершения очереди и путь загрузки в контроллере друзей.
