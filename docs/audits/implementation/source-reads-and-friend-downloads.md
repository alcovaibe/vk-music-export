# F13: адресные чтения подборок и подготовка скачивания друзей

База: `66fe54b4e15a800007f2fad783425b22f08a2005`, прежняя рабочая ветка `fix/audit-stage0-release-delivery-20261104`. Main, релизы, зависимости и музыкальная БД не меняются.

## Семантика действий

Открытие уже показанной подборки читает только выбранный источник. Полный каталог перед каждым открытием не перечисляется. При свежем полном снимке повторного чтения страниц нет. При изменившемся количестве строк полный ответ нормализует наблюдаемое описание подборки; это не продлевает TTL всего каталога.

Выбор «скачать этот трек» или конкретных строк друга означает exact-ID записи показанного списка. Номер позиции и occurrence считаются по полученному префиксу, даже если оставшиеся страницы ещё читаются. Для одной песни не создаются ключи задач всех 20 000 записей и не запрашиваются заново каталог/страницы. Движок по-прежнему разрешает точный ID и проверяет доступ перед transfer. Текущее членство записи в удалённой подборке этим действием не утверждается.

«Скачать всё» требует полного списка; частичный префикс не выдаётся за полный экспорт. Полная свежая наблюдаемая страница используется повторно. После истечения TTL выбранный источник читается один раз с обычной pagination; соседние источники и общий каталог ради этого не перечитываются. Наблюдаемые новые количество и порядок попадают в экран и очередь. Пустой ответ не запускает пустое скачивание и не очищает прежнюю очередь.

## Границы кэша и безопасности

Сохранены TTL 60 секунд, LRU, максимум 40 000 позиций / 64 полных источника, лимиты каталога и существующие проверки complete/count. Собственная музыка и разные друзья имеют разные ключи библиотек; каталог дополнительно связан с владельцем источника. Кэш по-прежнему привязан к viewer account, readSessionId и epoch. Новый reader не перепривязывает занятый кэш к другой сессии. Явное обновление каталога меняет epoch и отбрасывает его страницы, сохраняя пригодный снимок собственной библиотеки. Запоздавший writer старого epoch отклоняется.

При возвращении из загрузок пассивное обновление использует ещё пригодные наблюдения; кнопка явного обновления обходит их. Фоновая проверка скачанных подборок использует уже прочитанные полные страницы, но сохраняет проверки собственных файлов, SHA-256 и M3U8. Истёкший/неполный источник читается заново. Кэш не доказывает неизменность сервера за 60 секунд и не превращается в сохранённый verdict целостности файла.

Перед очередью остаются проверка владельца, повторная проверка сессии и проверка незавершённого скачивания. Logout/новый вход/отмена не могут подменить очередь. Свежий недоступный профиль не раскрывает ранее кэшированные треки. Токены и signed media URL не добавляются в кэш, журнал или диагностику. API и типы авторизации не расширяются.

Общий `MusicSourceReader` и `FriendDownloadPreparation` отделяют чтение/планирование от публикации UI/запуска сервиса. Это инкрементальная часть F26, а не заявление о полном разделении ViewModel. F12 (фоновые previews друзей) и F21 (классификация кода 201) здесь не объявляются закрытыми.

## Проверки

JVM-сценарии проверяют адресные чтения, owner/session/epoch, TTL без продления каталога, частичные страницы, отмену, changed count и 100/4500/20000 позиций с сохранением task key/occurrence. Android-сценарии используют настоящие ViewModel/контроллер и SQLite с fake API и детерминированными барьерами: повторное открытие, истёкшая подборка, одиночное скачивание из неполного списка друга, полный источник, смена входа/logout, отмена, passive/explicit refresh и свежий запрет профиля. Подменён только запуск transfer job; целостность/reuse и реальный Media3 продолжают проверяться существующими сценариями.

Каждое новое Android-имя обязательно для CI verifier; отсутствие или skip не дают зелёный результат. Локальные Python-проверки не заменяют компиляцию Kotlin и Android. Фактические результаты нужно связывать с новым SHA Actions. Живой VK-аккаунт, сетевые миллисекунды и физические телефоны этим изменением не объявляются проверенными.

## Регрессия, обнаруженная в проверках продолжения

В прогоне `42203172545` коммита `d29fba4630bac5e034d4abd88156c5da14cfc867` API 33 выполнил 215 сценариев: все десять новых SourceReadDeviceTest прошли, но serviceRecreationRetainsPausedQueueModesAndAllowsAnotherSelectedPosition не дождался playing после пересоздания сервиса (PlaybackDeviceTest:312). Это не объявляется ошибкой инфраструктуры или успешной проверкой.

При разборе найдена избыточная публикация child timeline в PlaybackMediaSource.updateMediaItem после изменения обложки. Она удалена: ExoPlayer 1.11.1 уже обновляет timeline в updateMediaSourcesWithMediaItems, а штатный ProgressiveMediaSource.updateMediaItem только сохраняет MediaItem. Публичное описание теперь volatile для чтения с application thread; ссылки CDN по-прежнему не раскрываются. Прямой Android-тест проверяет отсутствие повторного resolve и source-info callback при обновлении метаданных. Сценарий пересоздания и прежний тайм-аут сохранены; при падении он дополнительно выводит состояние плеера без учётных данных. Причинность единичного тайм-аута не утверждается только по статическому анализу; окончательный результат относится к следующему SHA CI.

В следующем прогоне `42206619040` API 33 уже прошёл, но API 29 завершился RemoteServiceException в LegacyAudioExportService после быстрого запуска/паузы. Внесён учёт отправленных, но ещё не promoted запросов: stopService откладывается до foreground-подтверждения каждого такого запуска. Старт и остановка синхронизированы маленьким ForegroundStartGate; новый явный старт отменяет прежнее намерение остановки, отклонённый запуск не оставляет pending ticket. Такой же переход используется сканированием дубликатов; superseded/cancelled scan и повторный старт сначала выполняют foreground promotion. Движок, файлы и модель UIDT API 34+ не заменяются.

Добавлены шесть JVM-сценариев, включая конкурентные stop/ack, и обязательный Android-сценарий двух быстрых запусков/пауз обоих сервисов в одном Main callback. Он пересекает пятисекундный системный deadline и проверяет, что очередь не выполнялась и не потерялась. На API 34+ этот legacy-only сценарий не утверждает исполнение FGS; там сохраняются существующие UIDT-проверки. После отключения рабочей среды локальные новые тесты не запускались: результат должен подтверждаться CI нового SHA.

Дополнительные прогоны выявили непостоянный тайм-аут Media3 на API 33; один из расширенных прогонов дошёл до успешного resume, но не запустил следующий выбранный трек. Полный player state добавлен для каждой фазы теста. В request-start сохранённый shuffle order теперь устанавливается после setMediaSources и до prepare/play, а не позже из publish: это устраняет окно запуска с ещё не восстановленным порядком. Связь каждого прежнего тайм-аута с этим окном не объявляется доказанной только статическим анализом.

Тестовый start явно устанавливает исходные shuffle-off и repeat-one через обычные команды, поскольку связанный service вправе сохранить режимы от предыдущей очереди. Сохранён исходный пользовательский случай со случайным shuffle, дополнительно проверяются все шесть порядков трёх записей. В каждом случае требуется настоящий playing, сохранение порядка/режимов/позиции и запуск второй выбранной записи после пересоздания. Тайм-ауты и обязательный полный набор не ослаблены. Отдельный ранний запуск API 33 не может заменить полный JUnit-отчёт. Фактический результат относится к CI следующего SHA; прежние красные прогоны не переименовываются в успешные.
