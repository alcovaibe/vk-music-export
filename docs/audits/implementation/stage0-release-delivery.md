В плане аудита этапы обозначены A–L. Здесь «этап 0» означает первый набор работ по F02 — согласованность публикации Latest и доставки обновления установленным приложениям. Весь этап C, F03/F05/F27 и ручная приёмка этим коммитом не закрываются.

## Что изменено

- Owner-requested promotion, как и стандартный stable publisher, вызывает `publish_channel()` с тем же проверенным APK. Сохраняется подготовленный JSON, затем создаётся отдельный PR канала и запускаются его проверки. Записи/слияния `main` в этом пути нет.
- Только release job получает недостающие `pull-requests: write` и `actions: write`, необходимые для PR и явного dispatch. Обычные build/PR jobs сохраняют read permissions. Пока эта ветка не слита, новые права workflow не используются существующим main.
- При повторе доставки уже открытый PR повторно получает dispatch проверок. Закрытый PR не открывается автоматически. До слияния summary явно показывает `pending review/merge`; ошибка доставки не превращается в успешный workflow.
- CLI `tools/update_channel.py --info ... --apk ...` позволяет повторить только доставку канала опубликованного проверенного APK, без повторной публикации. Частичный сбой с оставшейся веткой, но без PR, требует проверки оператором; автоматическое перезаписывание такого состояния не реализовано.
- Новый workflow `Update channel consistency` выполняет Python-тесты и офлайн-проверку схемы на push/PR. По расписанию (каждые шесть часов после попадания workflow в default branch) и при ручном запуске он сравнивает живой JSON именно из main с Latest и проверяет имя APK, размер и asset digest. Он ничего не записывает и не сливает. Метаданные API не доказывают повторную проверку подписи или minSdk внутри APK.
- В рабочей ветке подготовлен канал `0.12.1/1433`. Его публикация для пользователей произойдёт только после отдельно одобренного слияния. `version.properties`, теги, Releases, acceptance и настройки защиты main не изменены.

## Фактические проверки

В их числе orchestration owner promotion с синтетическими API/APK: вызов доставки точного артефакта, отказ PR, сохранение подготовленного JSON и неизменность `manual_acceptance=pending`; контрактные проверки стандартного stable/RC пути, запрет отката, повторный dispatch и обнаружение расхождения/подмены asset metadata.

JSON схемы рабочей ветки проверен. Android workflow проверяет схему в changes job даже при пропуске повторной сборки для JSON-only push; ошибка не может дать успешный aggregate interface. Оба изменённых/новых workflow разобраны YAML-парсером; это проверка синтаксиса, не доказательство выполнения Actions. `git diff --check` пройден.

Публичный APK Latest скачан 4 ноября: 5 969 335 байт, SHA-256 `3dac4905703c990d53a431b54cfd01ce12389db439943165d7a99ac30f6e3889`. Размер/хеш совпали с asset API. Из бинарного AndroidManifest извлечены package `app.alcovaibe.vkmusicexport`, версия `0.12.1/1433`, minSdk 29; debuggable не включён. Локальная повторная криптографическая проверка APK-подписи не выполнялась. Для исходного APK проверка подписи в прежнем CI описана в неизменённом аудите.

Новый checker проверен на реальном ответе Latest: подготовленный JSON совпадает, прежний JSON main `0.12.0/1343` даёт ожидаемую ошибку расхождения. Это read-only проверка API-снимка, без использования VK-аккаунта и без записи main.

Новые Android/Gradle/device-тесты и ручная приёмка не выполнялись: код приложения не изменён. End-to-end публикация/создание канального PR от Actions в этой работе намеренно не выполнялась — это потребовало бы нового выпуска. Возможный запрет создания PR через GITHUB_TOKEN остаётся явным административным условием; ошибка должна быть видима в CI.

2. После одобренного слияния проверить живой JSON/main и Latest read-only checker. До этого F02 в действующем канале остаётся открытым, хотя исправление подготовлено.
3. F03: отдельно согласовать/применить эффективную защиту main и проверить обязательные статусы; JSON ruleset сам ничего не включает.
4. F05: получить настоящие результаты приёмки точного APK; не менять pending на passed по результатам synthetic tests.
5. F27: определить долговременное хранение полного evidence. Текущий 30-дневный artifact retention этим набором не исправлен.
6. При следующем отдельно разрешённом выпуске проверить оба пути доставки и отсутствие автоматического слияния. Наличие PR ещё не означает доставку обновления пользователям.
