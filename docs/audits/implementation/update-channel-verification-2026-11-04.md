## Что изменено

- Python использует тот же строгий контракт stable JSON, что и Android: неизвестные поля, неверные типы и неканонические имена запрещены.
- Проверка кандидата анонимно скачивает настоящий публичный APK и проверяет размер, SHA-256, криптографическую подпись SDK apksigner, закреплённый сертификат и фактические package/version/minSdk/debuggable.
- Отдельная проверка действующего канала читает именно публичный raw URL. Она не выдаёт подготовленный JSON или открытый PR за доставку. Повторная проверка в конце отклоняет смену Latest/указателя во время загрузки; после main предусмотрено ограниченное ожидание CDN.
- Доставка восстанавливается после сбоя между созданием ветки, записью JSON, созданием PR и запуском CI. Закрытый PR, посторонние изменения или другой head блокируют повтор. CI привязан к проверенному полному SHA. Автоматического слияния и записи в main нет.
- Исправлено чтение сертификатов APK на Android 10. Текущие подписанты по-прежнему сравниваются строго; пустой сертификат, другой сертификат и повреждённая подпись не принимаются.
- Готовая загрузка сохраняется в отдельном журнале и восстанавливается после остановки процесса только после повторной проверки APK. Явная отмена удаляет загрузку и журнал. Путь ограничен выделенным каталогом и проверяется после canonicalization.
- Добавлены обработка внутреннего timeout и очистка позднего результата отменённого сервиса. Для этих защит есть регрессионные тесты; отдельный сбой реального сетевого сервиса с такими условиями не заявляется воспроизведённым.
- Будущая публикация должна прикладывать `release-evidence.zip` с build-info, публичным сертификатом, лицензиями, SBOM/OSV, upgrade-результатами и полными CI-отчётами. Внутренний манифест связывает файлы с точным APK через SHA-256; неполнота отчётов блокирует публикацию. Фактическое прикрепление к новому релизу в этой работе не выполнялось.

## Подтверждённые проблемы и исправления

### U-01 — P1: корректный APK отклоняется на Android 10

Файл: [app/src/main/java/app/alcovaibe/vkmusicexport/updates/GithubUpdates.kt:169](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/app/src/main/java/app/alcovaibe/vkmusicexport/updates/GithubUpdates.kt#L169).

Воспроизведение: run 41894518344, updater API 29. Реальный APK имел package приложения, code 1433 и minSdk 29, но archive SigningInfo был null; у установленного подписанного baseline 1343 сертификат присутствовал. Итог — INVALID_APK до установщика.

Причина подтверждена [исходником AOSP Android 10](https://android.googlesource.com/platform/frameworks/base/+/android-10.0.0_r1/core/java/android/content/pm/PackageManager.java): сбор сертификатов архива запускался при GET_SIGNATURES. Исправление запрашивает GET_SIGNATURES вместе с GET_SIGNING_CERTIFICATES и использует SigningInfo текущих подписантов. Исторические сертификаты не используются как обход проверки.

Проверка: API 29 прошёл реальное чтение/проверку APK и системную установку. На всех девяти API отклонены другой реальный сертификат и перепакованный APK с изменённым classes.dex, для которого намеренно задан правильный SHA-256 изменённых байтов.

Старый уже установленный APK не получает исправление кода через JSON. Для затронутого Android 10 первый переход на будущую исправленную подписанную сборку потребует обычной установки APK поверх приложения; новый такой APK ещё не выпущен.

### U-02 — P2: готовый APK теряется после изменения разрешения установки

Файлы: [app/src/main/java/app/alcovaibe/vkmusicexport/updates/GithubUpdates.kt:35](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/app/src/main/java/app/alcovaibe/vkmusicexport/updates/GithubUpdates.kt#L35), [app/src/main/java/app/alcovaibe/vkmusicexport/updates/UpdateController.kt:42](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/app/src/main/java/app/alcovaibe/vkmusicexport/updates/UpdateController.kt#L42).

Воспроизведение: в logcat API 30 run 41894518344 зафиксировано завершение процесса с причиной REQUEST_INSTALL_PACKAGES changed. Раньше состояние READY существовало только в памяти, а подготовка следующего запуска удаляла загрузку как orphan. Пользователь должен был скачивать повторно. Само завершение процесса воспроизведено в изолированном harness; потеря старого READY установлена анализом старого кода. Ручная проверка старого приложения на физическом телефоне не проводилась.

Исправление: небольшой отдельный журнал только проверенного APK; после запуска заново проверяются байты, manifest и сертификат. READY восстанавливается без сети. Повреждённые записи/файлы не восстанавливаются; выход сохраняет готовый APK, явная отмена удаляет его.

Проверка: два разных instrumentation-процесса на каждом API. Первый скачивает при запрещённой установке; затем выполняется настоящий force-stop, разрешение меняется вне тестового процесса, второй процесс восстанавливает APK при запрещённых перехватчиком сетевых запросах и открывает системную установку. Дополнительные Android-тесты проверяют повреждённый APK, абсолютный/выходящий за каталог путь и сохранность постороннего приватного файла.

### U-03 — P2: checker разрешает JSON, который Android отвергает

Файл: [tools/channel_contract.py:22](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/tools/channel_contract.py#L22).

Воспроизведение: дополнительное поле в корне или release ранее не отклонялось Python-checker, тогда как Android требовал точные наборы ключей. Следствие — зелёная проверка метаданных при неработающем обнаружении версии.

Исправление: общий строгий Python-контракт, включая типы чисел и канонические tag/APK/SHA-256. Проверка: отрицательные тесты неизвестных полей/типов, невалидных размеров и идентичности.

### U-04 — P2: повтор доставки после частичного успеха не восстанавливает PR надёжно

Файлы: [tools/update_channel.py:70](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/tools/update_channel.py#L70), [tools/update_channel.py:87](https://github.com/alcovaibe/vk-music-export/blob/c82228112194e46798e21a0d0c4abae2b7082222/tools/update_channel.py#L87).

Воспроизведение: stateful-тесты моделируют успешную операцию на GitHub и потерю ответа сразу после POST ветки, PUT файла, создания PR или dispatch CI. Раньше одного факта существования PR было недостаточно для доказательства его содержимого и проверяемого head.

Исправление: повтор читает фактический head, diff, содержимое JSON и состояние PR; не перезаписывает посторонние изменения, не открывает закрытый PR и не меняет main. Статусы pending_review / committed_waiting_public_verification / superseded / failed отличаются от доставки.

Проверка: после каждого моделируемого сбоя повтор не дублирует ветку/коммит/PR; изменённые repo/base/head и лишние файлы блокируют dispatch. Это тесты модели API, а не заявление об искусственном сетевом сбое на настоящем GitHub.
