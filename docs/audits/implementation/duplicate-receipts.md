# F08: поштучное хранение результатов поиска дубликатов

Дата: 4 ноября 2026. База: `597b0b8571c72f9c4cebeaa0930a97baada609a6`.
Ветка: `fix/audit-stage0-release-delivery-20261104`.

## Изменение хранения

Вместо полной перезаписи `duplicate-scan/checks.json` после каждой проверки используется отдельная `noBackupFilesDir/duplicate-scan.db`, schema1. Основная `audio-export.db` остаётся schema4. Таблицы: `duplicate_receipts` (owner + track_key, codec, SHA-256, signature_version=2, ordinal), `duplicate_state` (один активный аккаунт, поколение, fingerprint библиотеки, время создания, число результатов и следующий ordinal), `duplicate_import` (результат одноразового переноса). Первичный ключ owner + track_key и уникальный индекс owner + ordinal обслуживают адресный поиск и прежнее FIFO-ограничение в 20 000 результатов.

Новый результат записывается одной строкой и обновляет маленький счётчик в той же транзакции. Повторное сохранение той же записи обновляет её строку без перестановки FIFO. count() читает счётчик одним SELECT, get() одним индексным JOIN получает согласованный SQLite read snapshot владельца/поколения и receipt. Для попадания/промаха не захватывается writer transaction; повреждённая строка повторно проверяется в write transaction перед удалением. Накопленный список receipts не десериализуется после каждого трека. begin() один раз вычисляет fingerprint списка; при изменении набора/порядка адресно удаляет устаревшие ключи. Оставшиеся результаты не переписываются. Ключ по-прежнему исключает album; остальные поля NativeTrack входят в хеш как раньше. JVM-проверки сравнивают байты ключей с прежним алгоритмом.

Срок действия остаётся 24 часа от создания кэша. Достижение границы срока или перевод часов назад запрещают reuse; begin() создаёт новое поколение. Смена аккаунта очищает прежний набор, как в предыдущей реализации. Экземпляр с устаревшим поколением не может записывать в заменившийся кэш. Изменение snapshot также меняет поколение, сохраняя подходящие receipts. clear() сбрасывает только производные данные и отзывает старые экземпляры. Подключения закрываются в production-сценариях и тестах.

## Перенос и ошибки

Старый schema2 JSON, включая AtomicFile .bak, читается с прежним пределом 8 MiB / 20 000 receipts. Все строки проверяются до импорта. Строки, header и отметка импорта фиксируются одной SQLite-транзакцией; старый файл удаляется после commit. Ошибка IO/SQLite или abort не превращается в пустой успешный импорт: исходная копия остаётся, следующая попытка повторяет перенос. После commit с сохранившимся старым файлом отметка исключает повторный импорт.

Malformed/oversized JSON не является доказательством совпадения: отметка invalid сохраняется, исходные байты остаются в приватном каталоге до явного clear(), новый поиск может начаться с пустого кэша. Просроченные receipts не импортируются. Несовместимая или повреждённая строка новой БД не используется; адресное чтение удаляет только её и уменьшает счётчик в одной транзакции. Повреждение самой структуры SQLite автоматически не исправляется и не выдаётся за успешную проверку.

Старые ключи, включавшие album, преобразуются при begin() для текущих треков. Если album изменился до первого запуска миграции и остался только необратимый старый хеш, восстановить соответствие невозможно: такая запись проверяется заново. Обычные album-independent ключи сохраняются при изменении альбома.

SQLiteFull может откатить native-транзакцию до Android endTransaction. Обёртка сохраняет исходное исключение и добавляет ошибку cleanup как suppressed. Отказ не оставляет receipt без соответствующего счётчика. Полные аудиокопии, токены, CDN URL и согласия на удаление в новой БД не сохраняются. MusicDuplicates.remove и получение свежих сигнатур обоих файлов перед удалением не меняются.

## Проверки

Добавлены три JVM-теста совместимости ключей, изменения полей и границ TTL. Подготовлены девять точных обязательных Android-сценариев:

- перенос AtomicFile backup и старых album keys, reopen, reorder/смена альбома;
- abort в конце импорта, rollback всех строк/header и повторная попытка из неизменного JSON;
- malformed legacy и повреждённая строка/version не создают совпадений, пригодные строки сохраняются;
- аккаунт, TTL, rollback часов и смена snapshot запрещают устаревшую запись;
- abort после INSERT, настоящий SQLiteFull внутри receipt-транзакции и сохранность прежнего результата после reopen;
- clear() отзывает другие экземпляры, сохраняя очередь экспорта и реальный MediaStore MP3 с точными байтами;
- неподдерживаемые signature/version и отсутствие готового файла не создают receipt;
- чтение завершается, пока отдельный поток удерживает WAL writer transaction; чтение не должно ждать освобождения writer;
- нагрузки 100/4500/20000, reopen и адресное чтение, FIFO при 20001, перенос legacy JSON больше 2 MiB.

Прежние интеграционные сценарии отмены обработки, resume без повторной загрузки завершённого трека, локального хеширования проверенных файлов и обязательного свежего скачивания перед удалением сохранены. Fixtures обновлены для нового формата и закрытия SQLite; проверки бизнес-результата не убраны. CI verifier требует каждое новое имя. Проверки сбора замеров отвергают отсутствующие/дублированные/усечённые отчёты, другой API, неправильные workloads, нечисловые/неограниченные/отрицательные времена и неверные счётчики операций.

## Методика производительности

На каждом API — один синтетический прогон изолированной Android SQLite без VK и обработки аудио. Замеряются begin, сохранение N результатов, p95 save, reopen/begin/count и чтение всех N через get. SQL-триггеры считают INSERT/UPDATE receipts и записи маленького state; при первом заполнении должны быть N INSERT, 0 UPDATE и N+1 state writes. Повторный begin/read не должен менять эти числа. Нагрузки с измерительными триггерами не равны пользовательской задержке интерфейса.

`receipt_text_bytes` — сумма UTF-8 длин key/codec/SHA строк, `state_text_bytes` — generation/snapshot. Числа, индексы, страницы, транзакции и fsync в эти текстовые байты не входят. `legacy_min_text_bytes_estimate = receipt_text_bytes × (N+1) / 2` — расчёт нижней границы прежней повторной записи растущего набора, не измерение старого времени/износа. `observed_wal_size_bytes` — размер WAL в одной точке перед close, не накопленный объём физических записей. Heap/GC и физические WAL writes отдельно не измерены.

Из androidTest выводится ограниченный JSON тестового тега VKReceiptBench. Host-side logcat capture работает непрерывно во время instrumentation и сохраняет `interface-benchmarks/receipts-api-<API>.json`. F07-отчёты `api-<API>.json` продолжают проверяться. Теги отсутствуют в production-коде. Конкретные числа следует брать из успешного CI соответствующего SHA; разные CI-hostы и один прогон не позволяют ранжировать версии Android по быстродействию.

## Фактический статус перед CI

103 локальных Python-теста прошли (2.916 с), shell syntax и git diff --check прошли.
