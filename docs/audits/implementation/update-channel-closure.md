# Канал обновлений: условия закрытия

Рабочая ветка: `fix/audit-stage0-release-delivery-20261104`. Изменения main и выпуск релиза требуют отдельного разрешения владельца.

## Что проверяется автоматически

1. Точный JSON-контракт Python совпадает с Android: дополнительные поля и неверные типы запрещены.
2. Проверка кандидата получает Latest и анонимно скачивает его публичный APK. Проверяет размер, SHA-256, криптографическую подпись через SDK apksigner, закреплённый сертификат и реальный AndroidManifest (package/version/minSdk/debuggable).
3. Реальная доставка отдельно читает тот же raw URL main, который читает приложение. Подготовленный JSON или открытый PR не считаются доставкой.
4. Публикация указателя восстанавливается после сбоя каждого шага. Закрытый PR, посторонние изменения, изменившийся head, другая подпись или замена байтов той же версии останавливают процесс. Автоматика не пишет в main и не сливает PR.
5. Ручной запуск CI привязан к проверенному полному SHA; перемещение ветки до запуска отклоняется.
6. Будущая публикация прикладывает постоянный `release-evidence.zip`: build-info, сертификат, лицензии, SBOM/OSV, upgrade-проверки и полные CI-отчёты всех девяти API. Манифест архива содержит SHA-256 каждого файла и точного APK; отсутствие отчётов в CI блокирует публикацию. Ручная приёмка классифицируется отдельно и не выводится из зелёного CI.
7. На одноразовых AVD API 29–37 отдельный тест использует настоящие подписанные публичные APK 1343 → версия кандидата. Проверяет GithubUpdates (включая отказ другому реальному сертификату), FileProvider, системный установщик, сохранность UID и приватного файла.

Транспорт Android в этом тесте детерминированно отдаёт байты, заранее анонимно скачанные и проверенные на CI. Это не проверка сети конкретного телефона/оператора. Права установки выдаются только тестовому host на одноразовом AVD. Подтверждение установки выполняется через настоящий интерфейс Android. Приватный ключ production не нужен и не используется.

## Граница готовности

Нельзя объявлять 100% до выполнения всех условий:

- зелёные проверки текущего SHA, включая весь updater matrix;
- отдельно одобренное слияние указателя в main и успешная проверка публичного raw JSON/APK после слияния;
- включённая защита main (файл ruleset в репозитории сам по себе ничего не включает);
- проверка на физическом устройстве пути разрешения установки/скачивания/установки с сохранением реальной библиотеки;
- долговременное хранение доказательств релиза (F27), а не только ограниченный срок Actions artifacts;
- ручная приёмка реального аккаунта перед следующим stable (F05 остаётся самостоятельным условием).

Старые версии не меняются задним числом. Текущий стабильный APK не содержит новые исправления до отдельно разрешённого выпуска.

Матрица updater проверяет новую реализацию клиента на уже опубликованной паре APK 1343 → Latest. Новый подписанный APK будущего релиза отдельно проходит существующую signed-upgrade проверку на API 36. Эти результаты имеют разную область действия и не заменяют ручную приёмку будущего APK.

Предлагаемый ruleset рассчитан на одного владельца: обязательный PR, обязательные актуальные `build`, `interface`, `channel-delivery`, запрет force push и удаления main. Второй человек для одобрения PR не требуется. Шаблон не применён; изменение действующих правил требует разрешения владельца.

## Подтверждённый отказ Android 10

CI run 41894518344, updater API 29: реальный APK имел package `app.alcovaibe.vkmusicexport`, code 1433, minSdk 29, но `signingInfo` отсутствовал, тогда как у установленного baseline 1343 сертификат был доступен. В AOSP Android 10 `getPackageArchiveInfo()` вызывает `collectCertificates(skipVerify=false)` только при `GET_SIGNATURES`: https://android.googlesource.com/platform/frameworks/base/+/android-10.0.0_r1/core/java/android/content/pm/PackageManager.java .

Исправление запрашивает оба флага (`GET_SIGNATURES | GET_SIGNING_CERTIFICATES`) и по-прежнему сравнивает только текущих подписантов SigningInfo. Принятия пустого сертификата или произвольного сертификата нет. Интеграционный тест дополнен перепакованным APK с изменённым classes.dex и корректным для изменённых байтов SHA-256 — он обязан отклоняться на проверке подписи.

Установленный старый APK не получает исправления кода через JSON. Если устройство затронуто этим отказом, первый переход на будущую исправленную сборку потребует обычной установки подписанного APK поверх существующего приложения; удалять приложение или очищать библиотеку не нужно. Такой выпуск ещё не разрешён и не опубликован.

## Восстановление после разрешения установки

Run 41894518344 / API 30 logcat зафиксировал `Killing ... REQUEST_INSTALL_PACKAGES changed`: Android завершил процесс в момент выдачи разрешения. Это причина падения старого harness; разрешение теперь меняется между двумя отдельными instrumentation-процессами. В приложении добавлен журнал только уже проверенной загрузки (строгий JSON + имя файла в выделенном cache/updates). При старте повторно проверяются байты, manifest и текущий сертификат; только затем восстанавливается READY. Выход не удаляет готовую загрузку, явная отмена удаляет её и журнал. Повреждённый журнал/файл и путь вне каталога не восстанавливаются.

Обязательная матрица использует два процесса: скачать при запрещённой установке → настоящий force-stop → выдать разрешение → новый процесс восстанавливает READY при запрещённых тестом сетевых запросах → системный установщик. Ручной интерфейс выдачи разрешения на телефоне этим не заменяется.

Run 41897414632 / updater API 36: подготовка APK и восстановление прошли; подтверждению установки помешал ANR самого System UI. Диагностический run 41899126970 извлёк из сохранённого снимка «System UI isn't responding». Harness теперь может не более трёх раз обработать только точные известные диалоги System UI/Quickstep и только их системные кнопки, аналогично существующему emulator-dialog.py. ANR приложения не скрывается. Число обработанных диалогов записывается в proof.
